# Roadmap and open work

What Bobix still lacks, what is done but not released, and what nobody has verified yet. Update this file when an item lands, ships or changes. Last updated: 2026-11-11 (`develop` is v0.2.0-rc.5; the last release is v0.2.0-rc.4, the last stable one v0.1.3).

**Product direction (v3):** [product-direction.md](product-direction.md) records where Bobix goes next as a personal assistant for working well with Claude Code, in five build steps: measure usage, skills audit and model routing, a GitLab ticket flow, habits into skills, and a war room with its security ([#110](https://github.com/baonguyen-agilityio/bobix/issues/110)).

## 1. Done on `develop`, not released yet

- **Start only in Work** ([#178](https://github.com/baonguyen-agilityio/bobix/issues/178), for rc.8): Sessions and Work both started an issue, in different ways. Now Work is the one place: the Start box has **How**: **Full** (the ticket flow, the default) or **Quick** (a plain Claude session in the project folder with the issue's prompt, what Sessions' Start did). Resume and "waiting for a new session" moved to Work too, and a Quick start shows in Work under **Quick sessions** with its sessions. Sessions shows only Claude sessions grouped by issue (no To do list, no Next up); an issue there has **View in Work**. ⌘K's "Start #n" and the tour open the issue in Work. **Change folder…** next to the folder line in the Start box opens the folder dialog, checks the remote as Choose folder… does, replaces the remembered folder and prepares the box again; **Clone…** next to it clones a fresh copy with your own `glab` / `gh` (never into a folder that is there, not with under 1 GB free, and a failed clone leaves no folder) and does the same. A folder you chose or cloned now wins over the folder a session runs in; one that was deleted is not used (Start asks where the code is again); running flows keep their worktrees, and the box says that the folder serves every issue fixed in that project. Quick on an issue a session already works on offers Resume; Full on an issue whose flow runs points to it. Reading the issues again (the filter, the page arrows, Show issues, Refresh) shows "Reading your issues…" in place of the list at once, keeps only the newest ask's answer, names a host that failed or timed out, and stops reading either way. Overview, Stand-up and Today's report read the same lists as before. Checked in the real built app on macOS (debug build, real IPC) with a throwaway home, made-up repositories and stand-in `glab` / `gh` / `claude`, EN light, EN dark and VI; not on Windows or Linux, nor with the real Claude app.

Shipped on `develop` for the v0.2.0-rc.5 test build ([release notes](releases/0.2.0-rc.5.md)):

- **Skills audit and model rules** ([#111](https://github.com/baonguyen-agilityio/bobix/issues/111) backend, PR #125; the Skills screen, [#129](https://github.com/baonguyen-agilityio/bobix/issues/129), PR #130): step 2 of the [product direction](product-direction.md). Per project, it lists every skill Claude loads (personal, project, enabled plugins, claude.ai, managed), its uses over the last 30 days, the unused ones, the duplicate sets and the cost of the descriptions each turn. Disable and Remove (personal and project skills) keep a backup and can be undone; plugin skills are not changed, Bobix shows the `enabledPlugins` setting that would turn the plugin off. The "When to split, which model" block goes at the end of the project's `CLAUDE.md` only after you see the exact text, and Undo restores the file byte for byte. Nothing is written without a click. Checked on macOS in the smoke run (the audit, remove and undo, the rules block); not on Windows or Linux. Still open: the plugin settings are not edited, and the model advice at Start on a ticket and the pet's in-place tip (parts b and c of the direction) are not built.

The costumes ([#91](https://github.com/baonguyen-agilityio/bobix/issues/91)) are gone; picture pets keep their pixel look. `docs/media/demo.gif` and the demo video still show the pixel pets until they are re-recorded.

- **Ticket flow, GitLab first** ([#112](https://github.com/baonguyen-agilityio/bobix/issues/112), step 3 of the [product direction](product-direction.md)): the Work screen. An issue of a project on this computer gets **Prepare start**: Bobix shows how much disk is left (a worktree with a build takes about 5 GB; Start is refused below that), an optional **Ask Haiku to propose** (your own `claude -p`: small, or a split with a model for exploring, editing and reviewing) and the prompt, editable. **Start in Claude** makes a git worktree on a new branch `<number>-<title>` under the repository's `.claude/worktrees`, writes the work log's template into its self-ignoring `.bobix-log/`, and opens a Claude desktop session there; **Copy terminal command** gives the same start with `claude --model … --permission-mode plan` (the desktop link can't preset either). The session plans first with its assumptions; its plan (Claude's own `ExitPlanMode`) is held in Bobix until you press **Approve plan**, which puts that one session in Claude's auto mode, or **Ask for changes**. After that it runs to the end; Claude's auto mode stops it only for the four cases the prompt names. The work log (plan, steps, highlighted assumptions, result or blocker) shows under Work and in the session's details, a new assumption puts an amber "?" on the pet, **Fill gaps with Haiku** sums up from the log and the branch's commits, and **Clean up worktree** removes a finished one with `git worktree remove` (never forced; the log is kept). Bobix's plain Allow on any plan now works too: Claude ignored an approval that did not give the plan back. Checked end to end on macOS with a real Sonnet session on a throwaway repository and a stand-in `glab` (the smoke run's opt-in ticket step clicks the Work screen's buttons: Start, Approve plan, Fill gaps, Clean up), and the screen with made-up data in both themes, EN and VI. Not tried: the Claude desktop app itself (the same hook answer, but not run there), Windows and Linux (no free-disk reading on Windows: no cap there).
- **The ticket flow checks and reviews its work** ([#154](https://github.com/baonguyen-agilityio/bobix/issues/154), items 1, 2 and 7): the work log gets `## Checks`. Before done, the session runs the project's tests, build and lint and pastes each command with the last lines of its output (or says there are none), then reviews its change against the plan and the assumptions with `/code-review` and notes it there. Work shows ✓ n checks / ⚠ no checks and ✓ reviewed on done flows; done without checks is a warning in Work and on the Overview, not a block. **Review in Claude** (or **Copy review command**) starts a second session in the worktree that reviews the branch against its plan and writes what it found under Checks. The model-rules block and the warnings follow the current Claude Code docs: no "/compact at 60%", a new session or `/clear` first, the built-in Explore subagent named. Checked end to end on macOS with real sessions on a throwaway repository and a stand-in `glab`, and with made-up data in both themes, EN and VI.
- **Open MR from the ticket flow** ([#154](https://github.com/baonguyen-agilityio/bobix/issues/154), item 3, GitLab first): **Open MR…** on a done flow shows the merge request's title and description (closes the issue; the plan, the assumptions and the checks from the work log), editable; **Push and open MR** pushes the ticket's branch and runs your own `glab mr create`, then the flow links the MR. Clean up says how many commits no remote has before it removes the worktree. Checked end to end on macOS with a stand-in `glab` and a local bare repository as the push target (nothing sent to a real GitLab).
- **CI status and the CLAUDE.md check** ([#154](https://github.com/baonguyen-agilityio/bobix/issues/154), items 4 and 5): a flow with a merge request shows its head pipeline (passed, running, failed), read with your own `glab api` (a GET) at each issue read and on **Check CI**; a red one shows **Copy Fix CI** (a prompt for the ticket's session) and a stuck item "CI red for {x}" on the Overview. The Start box and Skills → the project say when the project has no CLAUDE.md or no test command in it, and offer `/init` or a one-line `Tests:` entry Bobix appends after a backup, with Undo. Checked end to end on macOS with a stand-in `glab` (a red pipeline, then a green one) and a throwaway repository.
- **Projects not found on this computer** ([#163](https://github.com/baonguyen-agilityio/bobix/issues/163)): a project counted as on this computer only once a Claude session ran in its folder, so a fresh clone could not start a ticket. Now Bobix looks for clones by their git remotes in the usual code folders (only `.git/config` is read) after each read of the issues; a project it doesn't find shows **Already on this machine: choose folder…** (the folder's remote is checked) and **Clone…** (your own `glab` / `gh`, on the click) under Work and Sessions → To do. Found, chosen and cloned folders are listed in Settings → Work → Project folders, each with Forget. Checked in the real built app on macOS with a throwaway home, made-up clones and a stand-in `glab`.
- **Pick repos, one list, GitHub tickets** ([#165](https://github.com/baonguyen-agilityio/bobix/issues/165)): Work listed only the issues assigned to you, GitHub was off by default with no hint, and the ticket flow was GitLab only. Now GitLab and GitHub are on wherever `glab` / `gh` is signed in (one switch each turns them off). **Repos to list** (Work, and Settings → Work) lists every repository or project you can reach, grouped by host, with a search and Select all / none; the first time, the ones active in the last 90 days are ticked, and your ticks are remembered. One list holds the open issues of the ticked repositories, newest update first, 20 a page, each with its repository and whom it is assigned to; **All / Mine / Unassigned** filters it (GitHub: one search per 30 repositories; GitLab: each project read on its own, with a warning past 20). "Not found on this computer" is gone: Start on a repository whose folder Bobix does not know asks once, **Choose folder…** (its remotes are checked: https, ssh, `~/.ssh/config` aliases, every remote) or **Clone…**, and remembers it. The ticket flow works on GitHub issues too: **Open pull request…** pushes the branch and runs your own `gh pr create`; its checks are read with `gh pr view` / `gh pr checks`, and a red one gives **Copy Fix CI** with `gh` commands. The code can live in another repository than the issue (the issue's Addendum): the Start box's **Fix it in which project?** picks it (remembered per issue repository), the worktree, MR / PR and CI go there, the MR / PR closes the issue across repositories, and **Start in another project…** gives one issue a flow per repository it needs, all listed on the issue.
- **Habits become personal skills** ([#113](https://github.com/baonguyen-agilityio/bobix/issues/113), step 4 of the [product direction](product-direction.md)): Skills → From your habits. With Settings → Usage → "Read my prompts" and its own weekly scan switch on (both off by default), once a week Bobix gives the prompts of the last 14 days to Haiku through your own `claude -p` (no session saved, no hooks) and keeps only the kinds of request with their weekly counts. A kind asked in each of the last two weeks is suggested, with its evidence; when a skill like it exists, Bobix proposes improving yours (or using a plugin's) instead. Draft runs `claude -p` with Sonnet and the skill-creator, with the best sessions' prompts as examples; you can edit it, and only Approve writes `~/.claude/skills/<name>/SKILL.md`. Every change is a version with Undo; a skill Bobix made is offered an improvement only on evidence from its uses (follow-up prompts, fix requests, tokens per use) and removal after 30 days unused. Checked end to end on macOS on a scratch HOME with made-up sessions and real Haiku / Sonnet calls; the panel with made-up data in a browser (both themes, EN and VI). Not on Windows or Linux, nor by eye in the app window.

- **War room over Tailscale** ([#114](https://github.com/baonguyen-agilityio/bobix/issues/114), steps 5 and 6 of the [product direction](product-direction.md)): the Room tab. One room per problem. People chat freely; at the end the host's one summarizer (their own `claude -p`) arranges the chat into problem → options → pros and cons, the host edits that draft and decides. The creator's machine hosts it on a second port bound to its Tailscale address only; people are identified by `tailscale whois` and only those the host invited get in. Only typed or pasted messages cross, with common secret shapes redacted on both sides; every join, view, message, record and refusal is in the room's audit log. Deciding writes a self-contained HTML record on the host, and each guest writes the same record from the room's data. Headless `claude -p` can't publish an artifact, so the host gets "Copy for Claude" (with a warning) instead. Checked: unit and security tests, and two Bobix backends in two processes with their own data and real `tailscale whois` identity (chat → real AI draft → edit → decide → the same record on both), over loopback: macOS's firewall holds an unsigned test binary listening on the tailnet address until someone clicks Allow. Not checked: two machines on a real tailnet, the panel by eye in the app window, Windows and Linux.

- **A pet leaves when its Claude is gone**: a session whose claude process ended without saying so (its terminal closed, a crash, a kill) is removed within about 5 s instead of staying on screen, waiting, until Bobix restarts. Only a process seen running as `claude` (or `node`) counts, so a shell between Claude and the hook never makes a live session look gone. Checked on macOS; Windows and Linux not yet.
- **Pets stay on top on Linux**: the pets window lost "always on top" once it had been hidden and shown again (seen on Ubuntu, Wayland through XWayland, v0.1.3: `alwaysOnTop: false` in Copy diagnostics). It is set again each time the window shows, and CI now fails if it isn't on top.
- **Pets take the mouse on Linux Wayland**: through XWayland, a pet could be hovered, clicked or dragged only while an X11 window (such as the panel) was under it. The pets overlay now has a window shape around the pets, so the X server hands them the mouse directly.
- **Linux dock**: the `.deb` sets `desktopName`, so its `.desktop` entry has `StartupWMClass=bobix`, the windows' real class (it said `Bobix`).
- **Panel on wide screens**: the details pane grows with the window (400 to 640 px) and the page may be 1,920 px wide instead of 1,440, so a full-screen panel leaves less empty space at the sides; scrollbars are thinner (10 px) and have no arrows.
- **Panel layout fixes**: a session row's title, level, folder and labels wrap instead of overlapping the status column or shrinking to nothing; rows collapse by the list's width, not the window's (the title shrank to 0 px at 981–1,100 px with details open); the panel shows once its labels and first sessions are in, so the top bar no longer jumps on open, and when it wraps the connection status stays on the right; sessions that arrive before the settings no longer throw (the board was drawn in part until the settings came); a hovered pet's card sits above other pets' bubbles.
- **Panel**: the final report shows the answer's Markdown (lists, tables, code) and keeps up to 32,000 characters instead of 600 on one line, and folds away with a click; status pills sit in the middle of their row; the log puts the time on one line, marks each kind of event, folds repeats ("×3") and shortens long commands in the middle (whole on hover); details never scroll sideways; text of the same kind has one size (the session's title in its details had lost its size to the Setup cards' heading rule).
- **Open session**: a CLI in the Claude app's own terminal brings the Claude app forward, also on Wayland, and is named "Claude" (it was "claude-desktop" and could not be opened).
- **A pet's shape comes from its project, its colour from its session**: every session of a project, and of its git worktrees (Claude desktop makes one per session), has the same creature, each session in its own colour. When a session of the project ends or starts, the others' colours change in the panel's list, its details and on the pets at once (they used to keep the old colour until something else changed). A project can get its own picture as the pet's face (PNG, JPG, GIF or WebP up to 2 MB, from the panel's Change pet; Default pet undoes it). Pictures stay in the app's data folder; GIFs stay animated.
- **Pet pictures as pixel art** (hidden for now, [#138](https://github.com/baonguyen-agilityio/bobix/issues/138): it is redone in the flat style in #139; the code stays behind `PICTURE_PETS` in `src/ui/creature.js`, and saved pictures are kept): a picture chosen in **Change pet** opens a dialog that shows it as pixel art, on its own and on the pet. You choose whether it is the face in the project's creature (each session keeps its colour) or the whole pet, and set the size (32, 48 or 64 px), the number of colours and accent colours, stray-pixel clean-up, the outline (a darker shade of the picture's darkest colour, or a colour of your own: a swatch, the colour picker or a typed code such as `#f0a`, `rgb(255 0 128)` or `hsl(200 80% 40%)`) and background removal, and save when it looks right; **Edit picture** reopens it from the stored original. A GIF stays animated. A WebP picture is decoded in a hidden page (first frame only): Electron's `nativeImage` can't read WebP on Linux.
- **Show when needed** (#55, Settings → Pet mode): nothing on the edge; only a session that needs you (waiting, just done, context under 25%) shows, its pet hanging under the app's pixel balloon and rising from below the screen to past the top, in its own column away from the pointer and the other pets, again and again until the need is over (a finished task crosses once). Pointing at it stops it and opens its card (Allow / Deny while it waits); answering pops the balloon. A corner pill counts the sessions and lists them with Allow / Deny. **Do not disturb** 30 / 60 min (Settings) hides the pets in both modes and the notifications; the pill can end it. More pets than fit take turns instead of folding into "+N". Each pet shows its own state with an effect kept to its own slot (a tight pulsing outline while it waits, the tool held in its hands, a compact XP bar, battery and goodbye), and no status balloon while effects run (balloons come back with reduced motion). Pointing at a pet stops the whole line and shows that pet's card or its request with Allow / Deny; a click opens that pet's session. Dragging a pet (with its family) takes it out of the line; let go and it slides into the line at the nearest free place. A real-Chrome test reads the composited overlay and fails on any effect pixel over another pet, tag or balloon, or two pets in sight overlapping.

While at most two of them need you, each pet holds a pixel balloon (orange "!" waits for you, green tick is done; a press opens its card with Allow / Deny); from three, one bubble sums them up and opens the family card. The approval countdown no longer redraws (and flickers) the card every second.
- **Feedback** (a button at the top of the panel on every tab, and the tray menu): a bug or an idea opens GitHub's new-issue form, filled in, and the person submits it themselves. Errors of the main process are kept in memory for it, so a crash is not captured.
- **Quest and log in full**: the details keep the whole prompt (up to 32,000 characters; a longer one ends in "[…]" on its own line) and show it as Markdown, like the final report (tables, nested lists, code, quotes); Quest shows its first lines and each log line 2, with **Show more** where there is more. The session row, the log and the pet's card show the prompt without its Markdown signs.
- **Permission requests wait on the pet until you answer**: a new install holds a request in Bobix until it is answered there (or Esc in the terminal) instead of 60 s; a time limit can still be set, and stored settings keep their value. Nothing is held while pets are hidden or notifications are paused.
- **Clicks reach the app under the pets again**: a pet dragged while its session ended left the drag open, and the whole strip at the bottom of the screen kept the mouse (Claude's prompt box there could not be clicked) until Bobix restarted; letting go anywhere now ends the drag.
- **Family card and balloons, fixed after an audit**: the family card's Allow / Deny / Open buttons take clicks (they passed through to the app below) and the card opens above the summary bubble, which closes it again; the card sits above other pets; the "+N" balloon takes clicks and goes after 90 s like the side sessions' own; on the Top edge balloons hang below the name tag instead of off the screen; a pet that stops next to a family keeps clear of its side sessions and a pet on its own stays above a family it walks past; a family's name tag stops at the screen's ends; an unknown context shows an empty bar on the pet card; running Bobix from a clone no longer turns "start at login" off for the installed app.

- **Work items** (first version): a session's details show its git status (branch, changed files, commits not pushed, ahead / behind its upstream, last commit, worktrees), read locally with `git` at most every 30 s. A new **Work** tab lists the open GitLab issues assigned to you, grouped by project (projects whose repository a session used here first, the rest under "Not seen on this machine"), with labels, due date, a link to the browser and the session working on it, and a Projects dropdown to show only the projects you pick (all by default; filtered in the app, no extra request): a branch named `<number>-…` (GitLab's branch from an issue) in a repository of that project links the session to the issue, and the session shows `#<number>`. Off by default; one switch in Settings, no URL to type: Bobix asks your own `glab` which GitLabs it is signed in to (`glab auth status`) and reads the issues of each (a host whose sign-in fails is left out). Bobix keeps no token; if glab is missing or signed in nowhere, the tab says to run `glab auth login` yourself. Read-only. Checked on macOS against a self-hosted GitLab (21 issues, same as `glab api`); Windows, Linux and gitlab.com not yet.
- **Panel as a status board**: the panel is a board with one column per state (To do, Waiting for you, Working, Just done, Resting), cards instead of rows, and a session's details in a drawer from the right. To do holds the GitLab issues no session in the list works on (with New or Resume, the Projects picker and Refresh), so the Work tab is gone; an issue with a session shows as that session's `#<number>`, and Open session in its details resumes it. A waiting request can be answered on its card. Below 900 px one column shows at a time, picked from a row of chips. Warmer colours, and a dark look that follows the system. Checked from source on macOS with pretend sessions (light, dark, 1180 and 420 px); not yet with real sessions or on Windows / Linux.
- **Start work from an issue**: each issue of a project on this machine has one button on its card in the To do column. **Resume** opens the session working on it: one in Bobix's list (same as a click on its pet), else the newest Claude desktop session in the project's folder named `[<CODE>-<number>]…` (or `<project> #<number>…`, the first format) (read from Claude desktop's own session list, so it works after Bobix restarts; archived ones are left out). **New** opens a new Claude desktop session in the project's own folder with Claude's documented `claude://code/new?folder=…` link (no prompt sent) and the issue shows "Waiting for a new session ✕ Cancel": the first session *created* in exactly that folder afterwards takes the issue, whatever other sessions are open there (open, resumed, cleared or forked sessions never count as created), and is named `[<CODE>-<number>] <short title>`, e.g. `[BAK-23] Fix the login`, through Bobix's SessionStart hook (`sessionTitle`, the same as `/rename`). A project's code is made from its name (first two letters of the first word and the first letter of the last: `ba-qa-kit` → `BAK`, one word: its first three letters) and can be set per project in Settings → Project codes. No question, nothing guessed from timing, nothing stored by Bobix besides the codes you set. A session also works on an issue when a branch it was on names it (`<number>-…`); a side session takes its parent's issue.

Everything before that is in v0.1.3 (2026-11-04), see its [release notes](https://github.com/baonguyen-agilityio/bobix/releases/tag/v0.1.3).


Release checklist: bump `version` in `package.json` → tag `vX.Y.Z` → check the 5 fixed-name files are attached → add release notes.

## 4. Known limits (by design or outside Bobix's control)

- Builds are not code-signed: macOS and Windows warn on first launch.
- Linux Wayland: no app may bring another app's window forward, so a click on a terminal session's pet opens it in the panel and names the terminal instead. Sessions in the Claude desktop app open directly.
- Linux Wayland: through XWayland, Bobix sees the cursor only while it is on a pet, so fading near the cursor works only right next to a pet.
- Linux Wayland: no app may bring another app's window forward, so a click on a terminal session's pet opens it in the panel and names the terminal instead. Sessions in the Claude desktop app open directly, and a CLI in the Claude app's own terminal brings the app forward (not its terminal tab).
- Opening a session in the Claude desktop app uses `claude://code/continue`, not a documented API; it may change.
- While Bobix holds a permission request, Claude Code shows its own permission prompt in the terminal at the same time (checked with Claude Code 2.1.318), so an answer in either place goes through and a stuck Bobix never blocks Claude. Not checked: the Claude desktop app's own prompt, and older Claude Code versions.
- Approvals need the Node.js forwarder; with the curl / PowerShell fallback Bobix only watches.
- Linux installers are `.deb` only (Ubuntu, Debian). Other distributions aren't packaged.
- Only Claude Code sessions (terminal, IDE, the Code tab of the Claude app). Ordinary chats in the Claude app or on claude.ai have no hooks, so Bobix can't follow them.
  - Checked on 2026-11-04 on macOS while a chat answered: Claude desktop's logs (`~/Library/Logs/Claude`) record nothing about chats, and the only chat-related writes are to claude.ai's internal IndexedDB, which keep happening after the answer ends, so they can't serve as a status. Reading that database would mean reading private chat data in an undocumented format.
  - Not tried, decided against for now: reading the app's UI through the Accessibility API (e.g. whether a "Stop" button is showing; needs the Accessibility permission and breaks when the UI changes), and a browser extension for claude.ai on the web (does not cover the desktop app).
- To do column, issues and sessions:
  - A project gets New / Resume only once a session Bobix saw since it started used its repository; after Bobix restarts, a project is under "Not seen on this machine" until one of its sessions does something.
  - After New, if you don't create the session, the next session you create in that folder later takes the issue. Cancel it with ✕ on the issue's card. The wait is kept in memory only: a Bobix restart drops it.
  - Resume after a restart finds the session by its name in Claude desktop's session files (not a documented format). A session you rename yourself, or one named with a project code you changed since, is not found; the button says New again. Several sessions of one issue: Resume opens the one used last.
  - Several main sessions in one project folder share its files and can edit the same ones; Bobix doesn't prevent it. Side sessions Claude starts get their own worktree.
  - Only the first 100 open issues per GitLab are read. The same project path on two GitLabs counts as one project.
- Memory is about 330–400 MB (Electron).
