# Roadmap and open work

What Bobix still lacks, what is done but not released, and what nobody has verified yet. Update this file when an item lands, ships or changes. Last updated: 2026-11-14 (`develop` is v0.2.0-rc.8; the newest release is the pre-release v0.2.0-rc.8, the newest stable one v0.1.3). What must be true before 0.2.0 is tracked in [#195](https://github.com/baonguyen-agilityio/bobix/issues/195).

**Product direction (v3):** [product-direction.md](product-direction.md) records where Bobix goes next as a personal assistant for working well with Claude Code, in five build steps: measure usage, skills audit and model routing, a GitLab ticket flow, habits into skills, and a war room with its security ([#110](https://github.com/baonguyen-agilityio/bobix/issues/110)).

**Platforms:** macOS decides a release. Windows and Linux are covered by the CI smoke run and then tried by a person on a real machine; what still fails there goes under known limits (section 5), not into a promise.

## 1. Done on `develop`, not released yet (after rc.8)

- **A Full start interviews you before the plan** ([#216](https://github.com/baonguyen-agilityio/bobix/issues/216), for rc.9): the Full start's instructions (not Quick's) tell Claude to restate the ticket and wait for your confirmation, then ask in rounds through `AskUserQuestion` (about 8 at most) only what the ticket and the code cannot answer. Each question names its source (a ticket quote or file:line), carries a tag (scope / approach / edge case / done criteria) and offers "Out of scope for this ticket" (kept under `## Later`, out of the plan); "up to you" goes to Assumptions; a clear ticket gets one "No questions, because …" line. The plan ends with a Mapping table (requirement → step, answer → step). The work log has new sections `## Ticket`, `## Questions`, `## Later`, `## Mapping`; the parser keeps them and Work shows them. The method is in Bobix's own text, no skill needed. Unit tests cover the rules text and the parsing. While Claude asks (`AskUserQuestion`, seen as a PreToolUse or a PermissionRequest) the pet shows waiting with the question as its text and Bobix notifies once; Bobix never holds or answers that request, because an Allow without the answers would skip the question (Claude's hooks docs: "allow" alone is not enough for it), so you answer in Claude's own window. **To be verified by the owner's real ticket:** a full interview in Claude Desktop and in the terminal command.

## 2. In the test builds (v0.2.0-rc.1 to rc.8), no stable release yet

Release notes: [rc.5](releases/0.2.0-rc.5.md), [rc.6](releases/0.2.0-rc.6.md), [rc.7](releases/0.2.0-rc.7.md), [rc.8](releases/0.2.0-rc.8.md). The last stable release is v0.1.3 (Electron); the test builds are the Tauri app.

- **The hover card says what the session works on, and holds still** ([#100](https://github.com/baonguyen-agilityio/bobix/issues/100), part of it, in 0.2.0-rc.8): while a session works, the status row names the file or command its tool works on (a long path keeps its file name, whatever its separator; a long status gives way to the badges instead of running over them; the permission request text and its notification keep a long path's end too, the activity log is unchanged); a card or bubble already on screen is redrawn without its entrance, so it no longer flickers while tools run; "No quest yet" is no longer shown on the card. Still open from #100: the context meter (context used, coloured) and the card's layout.
- **The Chrome tests no longer fail on a slow or stalled runner** ([#155](https://github.com/baonguyen-agilityio/bobix/issues/155)): on 2026-11-14 `test/overlay.test.js` (Ubuntu: Chrome slow to start, then the file hung to its timeout) and `test/layout.test.js` (Windows: a DevTools call got no answer) failed about six times with no real defect. Both now share `test/chrome-helper.js`: Chrome is started up to 3 times (20 s each, with its stderr in the message), every DevTools call has 30 s and one resend, Chrome and its profile are always removed and the server always closed, and the two steps have a `timeout-minutes`. The same runs showed one real panel bug behind the layout test's "the pointer leaving does not hide the tip" (macOS, PR #207): a "?" tip replaced under the pointer (by a scroll or a redraw) lost its "out" event and stayed on screen; the pointer's next "over" on anything else now starts the hide (the test failed in about half of the local runs at 420 px before, 0 of 8 after). Checked locally on macOS and by repeated CI runs on the pull request; the checks themselves are unchanged.
- **Update Bobix from inside the app** ([#189](https://github.com/baonguyen-agilityio/bobix/issues/189), in rc.8): a new version shows **Update** in the notification (a button on macOS), the tray and Settings → App → Updates; nothing is downloaded until it is pressed, held permission requests and running ticket flows are named before the restart, **Check now** works with the daily check off, and **Get test builds** (off by default) adds `-rc.N` versions, never a downgrade. Signed update files and two update lists (`latest.json`, `test.json`) come from the release workflow ([Update feed](development.md#update-feed)). **Unverified:** the owner's key pair exists (key id `6C8CB60511EB2B2F`: the public key is in `tauri.conf.json`, the private key and its password are secrets of the GitHub Environment `release`) and rc.8 is the first signed release (checked up to its signed update list), so no real update has run yet: that needs rc.9. Tried on a Mac with a throwaway key and a local source, **not** on Windows, nor on Linux (a real Ubuntu desktop decides whether Linux keeps it, else it keeps the link); the CI step that updates from the previous build is not built. - **A card closes when the cursor leaves the pets on XWayland** ([#101](https://github.com/baonguyen-agilityio/bobix/issues/101), in 0.2.0-rc.8): moving from a pet onto a Wayland window (Claude Desktop, say) left the pet hovered and its card open, since there the page's own mouse events are all it knows of the cursor; leaving the window now clears it. - **A Full start in Claude runs in the flow's worktree, and the flow follows its session** ([#188](https://github.com/baonguyen-agilityio/bobix/issues/188)): a Full start opened with Start in Claude never ran in the flow's worktree, so the flow stayed "waiting for its session": no plan gate, no checks, no MR. Cause, read in the Claude desktop app (5.11492.0): its `claude://code/new?folder=` handler cuts any folder at or under `<repo>/.claude/worktrees/<name>` down to `<repo>`, and Bobix made its worktrees exactly there. Now the worktree is `<repo>/.bobix/worktrees/<repo's name>-<number>` (a folder that ignores itself), which the link keeps. The session whose first prompt names the issue takes the flow wherever Claude opened it: in the flow's worktree (also the terminal command) as before; in a worktree Claude made for the session, the flow works there (its folder, its branch, the work log, the checks, Open MR) and says so; in the repository's main folder, the flow keeps its own worktree, the prompt tells the session to `cd` into it, and Work says so with how many files of yours were not committed there. Clean up and Remove only ever delete the folder Bobix made, and say what is not pushed, also when the worktree was deleted by hand (Open MR then pushes from the repository). A branch with nothing committed is not pushed. A start that waits when Bobix closes waits again after the restart; a plan approved in Claude itself moves the flow on; a session with its code in another repository than its issue is listed under that issue; Review in Claude names the branch and folder to review. A worktree kept from before, in the old place, is used again by a new Start. Checked in the real built app on macOS (debug build, real IPC, throwaway home, made-up repositories with local push targets, a stand-in `glab`, pretend sessions through the real hook, EN and VI), and the links Bobix opened were given to the Claude app's own folder function: all kept. Not tried: the real Claude desktop app (what it does with the folder once the page has it, and where it puts its own worktree, are read in its code, not run), Windows and Linux (paths by unit test only).
- **The process is in the repository** ([#196](https://github.com/baonguyen-agilityio/bobix/issues/196)): `CLAUDE.md` (test commands, working rules, which model for which step), shared `.claude/settings.json`, a pull request template with the definition of done, `SECURITY.md`, weekly Dependabot pull requests (cargo, npm, GitHub Actions) and an automatic Claude review (`claude-review.yml`, comments only, never blocks); `docs/development.md` has the Process section and the release steps for a protected `develop` (a version bump is a pull request). - **A started session gets its name in every start path** ([#184](https://github.com/baonguyen-agilityio/bobix/issues/184)): a Full start in Claude (seen with the code in another repository) left the session unnamed and the flow "waiting for its session". Cause: Claude desktop did not open the session in the flow's worktree the link named; it started in the repository's main folder (in Claude desktop's own session records, no session ever ran in a Bobix worktree), while Bobix waited only in that worktree. Now a start waits where its session may come up (that folder, its repository's main folder, a Claude worktree there) and the new session takes it with its first prompt, once that names the issue; the name is `[<code of the issue's project>-<number>] <title>`. Several starts can wait in one folder, the same issue in two repositories each gets its own session, and a session you open there yourself, one open before the start, or one after Cancel takes none. The UserPromptSubmit hook now runs in the foreground, like SessionStart (older installs are refreshed at start). The flow did not follow that session yet: fixed in the #188 item above ([#188](https://github.com/baonguyen-agilityio/bobix/issues/188)). Checked in the real built app on macOS with made-up repositories and stand-in `glab` / `claude`; not with the real Claude app.
- **The automatic review also checks the docs, and says when it skipped** ([#204](https://github.com/baonguyen-agilityio/bobix/issues/204)): `claude-review.yml` has a second Opus step that comments where a README, the site, `docs/`, `CLAUDE.md` or an app string (EN and VI) no longer matches the change (stale file and line named, silent on a change nobody sees, no repeat after a new push). When the action skips itself (the workflow differs from `main`) the job shows a warning and a summary note instead of looking passed. The file must be identical on `main` and `develop`, so a change to it is two pull requests. Checked on a real pull request (a test change that renamed one EN string, since closed): the docs check left 6 comments, each naming a stale file and line; after the docs were fixed, a second run did not repeat them and added 2 new valid ones. Cost per run, from the logs: the code review about 9 turns, 75 s, 0.54 USD; the docs check 12 to 14 turns, 30 to 36 s, 0.24 to 0.45 USD. Not tried: a docs-only pull request.
- **The work log follows Bobix's language** ([#185](https://github.com/baonguyen-agilityio/bobix/issues/185)): a Full start tells the session to write the work log in Bobix's language (plan, assumptions, steps, notes under Checks, what blocks it, the result), keeping code, commands, their output and the log's headings and markers as they are; the flow keeps the language it started in. What the team reads stays English: commit messages, and the MR / PR description, which the session writes in its own `## MR (English)` section (Open MR… uses it; without it the box says so and offers the request to copy). Fill gaps and the review session follow the flow's language. English users see no change. Fill gaps now shows its summary at once (the flow's details are read again). Checked in the real built app on macOS with a stand-in session that writes a Vietnamese log, EN and VI.
- **Did your changes help?** ([#181](https://github.com/baonguyen-agilityio/bobix/issues/181)): Skills → Did it help? measures the effect of each change on your own sessions, on this computer only (nothing is sent, no number is built in). Every change made through Bobix is noted with its date and project (a skill disabled, removed or undone, the Tests line, the model rules, a habit skill's version, the model split of a ticket; changes of one kind in one project within an hour are one step). Each step is compared on the 20 sessions in its project just before and just after it: medians, n and a range from the quartiles, "within noise" when the range crosses zero or the change is under 5%, and "not enough data yet" with no number below 10 sessions a side. Two steps in the same sessions are said to overlap and get no number; another model between the windows and a different mix of split and plain tickets are warned about. Skill changes are judged by the first turn's input (measured) instead of chars ÷ 4, which stays only as a labelled estimate; the model split compares tickets with it against tickets without (tokens measured, money from your price table as an estimate, left out when a model has no price). Your usual session per project (tokens, first turn, re-read share, turns, prompts, minutes, per ticket) and Bobix's own `claude -p` calls of the last 30 days are shown too. `usage.json` now keeps 1000 sessions with their project, first-turn input and prompt count, and reads back transcripts of the last 90 days (400 at most). Checked in the real built app on macOS with made-up transcripts in a throwaway home, EN light, EN dark and VI; not on Windows or Linux.

Looking up `glab` / `gh` / `claude` takes 5 s at most per shell and happens once per app start and on Refresh. Every command Bobix runs is stopped with everything it started at its time limit (process group; job object on Windows) and is never waited on past a 2 s drain; a clone that ran out of time has its unfinished folder removed only once nothing it started still writes there. The pages get the state at most 4 times a second and only when it changed; flows go without their work log, plan and MR draft (read when a flow's details open), and only the 20 newest cleaned flows stay (their logs are kept in `worklogs/`): one state frame with 200 flows went from 30.5 MB to 50 KB. A first read ticks only the 10 most recently active repositories and says how many more were active. Full start fetches first (30 s at most; offline it starts from the last copy and says from when), starts from the remote's real default branch and refuses with why when there is none; your uncommitted Tests line in CLAUDE.md is copied into the new worktree, and the Start box says which folder that button edits. The clone search runs once per app start and on Refresh, and on macOS walks Desktop, Documents and Downloads only after **Find on this Mac**. Under 5 GB free the Start box warns and offers **Start anyway** and **Quick start instead**. Folders are compared as folders (separators, a trailing one, case on Windows and macOS). Checked in the real built app on macOS (debug build, real IPC, throwaway home, made-up data, stand-in `gh` / `claude`, EN light, EN dark and VI); Windows paths and the job object by unit tests and CI only.
- **Start only in Work** ([#178](https://github.com/baonguyen-agilityio/bobix/issues/178), for rc.8): Sessions and Work both started an issue, in different ways. Checked in the real built app on macOS (debug build, real IPC) with a throwaway home, made-up repositories and stand-in `glab` / `gh` / `claude`, EN light, EN dark and VI; not on Windows or Linux, nor with the real Claude app.

- **Ticket flow, GitLab first** ([#112](https://github.com/baonguyen-agilityio/bobix/issues/112), step 3 of the [product direction](product-direction.md)): the Work screen. An issue of a project on this computer gets **Prepare start**: Bobix shows how much disk is left (a worktree with a build takes about 5 GB; Start is refused below that), an optional **Ask Haiku to propose** (your own `claude -p`: small, or a split with a model for exploring, editing and reviewing) and the prompt, editable. **Start in Claude** makes a git worktree on a new branch `<number>-<title>` (under the repository's `.claude/worktrees` at first; since #188 under `.bobix/worktrees`, see section 2), writes the work log's template into its self-ignoring `.bobix-log/`, and opens a Claude desktop session there; **Copy terminal command** gives the same start with `claude --model … --permission-mode plan` (the desktop link can't preset either). The session plans first with its assumptions; its plan (Claude's own `ExitPlanMode`) is held in Bobix until you press **Approve plan**, which puts that one session in Claude's auto mode, or **Ask for changes**. After that it runs to the end; Claude's auto mode stops it only for the four cases the prompt names. The work log (plan, steps, highlighted assumptions, result or blocker) shows under Work and in the session's details, a new assumption puts an amber "?" on the pet, **Fill gaps with Haiku** sums up from the log and the branch's commits, and **Clean up worktree** removes a finished one with `git worktree remove` (never forced; the log is kept). Bobix's plain Allow on any plan now works too: Claude ignored an approval that did not give the plan back. Checked end to end on macOS with a real Sonnet session on a throwaway repository and a stand-in `glab` (the smoke run's opt-in ticket step clicks the Work screen's buttons: Start, Approve plan, Fill gaps, Clean up), and the screen with made-up data in both themes, EN and VI. Not tried: the Claude desktop app itself (the same hook answer, but not run there), Windows and Linux (no free-disk reading on Windows: no cap there).
- **The ticket flow checks and reviews its work** ([#154](https://github.com/baonguyen-agilityio/bobix/issues/154), items 1, 2 and 7): the work log gets `## Checks`. Before done, the session runs the project's tests, build and lint and pastes each command with the last lines of its output (or says there are none), then reviews its change against the plan and the assumptions with `/code-review` and notes it there. Work shows ✓ n checks / ⚠ no checks and ✓ reviewed on done flows; done without checks is a warning in Work and on the Overview, not a block. **Review in Claude** (or **Copy review command**) starts a second session in the worktree that reviews the branch against its plan and writes what it found under Checks. The model-rules block and the warnings follow the current Claude Code docs: no "/compact at 60%", a new session or `/clear` first, the built-in Explore subagent named. Checked end to end on macOS with real sessions on a throwaway repository and a stand-in `glab`, and with made-up data in both themes, EN and VI.
- **Open MR from the ticket flow** ([#154](https://github.com/baonguyen-agilityio/bobix/issues/154), item 3, GitLab first): **Open MR…** on a done flow shows the merge request's title and description (closes the issue; the plan, the assumptions and the checks from the work log), editable; **Push and open MR** pushes the ticket's branch and runs your own `glab mr create`, then the flow links the MR. - **CI status and the CLAUDE.md check** ([#154](https://github.com/baonguyen-agilityio/bobix/issues/154), items 4 and 5): a flow with a merge request shows its head pipeline (passed, running, failed), read with your own `glab api` (a GET) at each issue read and on **Check CI**; a red one shows **Copy Fix CI** (a prompt for the ticket's session) and a stuck item "CI red for {x}" on the Overview. - **Projects not found on this computer** ([#163](https://github.com/baonguyen-agilityio/bobix/issues/163)): a project counted as on this computer only once a Claude session ran in its folder, so a fresh clone could not start a ticket. Now Bobix looks for clones by their git remotes in the usual code folders (only `.git/config` is read) after each read of the issues; a project it doesn't find shows **Already on this machine: choose folder…** (the folder's remote is checked) and **Clone…** (your own `glab` / `gh`, on the click) under Work and Sessions → To do. Found, chosen and cloned folders are listed in Settings → Work → Project folders, each with Forget. Checked in the real built app on macOS with a throwaway home, made-up clones and a stand-in `glab`.
- **Pick repos, one list, GitHub tickets** ([#165](https://github.com/baonguyen-agilityio/bobix/issues/165)): Work listed only the issues assigned to you, GitHub was off by default with no hint, and the ticket flow was GitLab only. Now GitLab and GitHub are on wherever `glab` / `gh` is signed in (one switch each turns them off). **Repos to list** (Work, and Settings → Work) lists every repository or project you can reach, grouped by host, with a search and Select all / none; the first time, the ones active in the last 90 days are ticked, and your ticks are remembered. One list holds the open issues of the ticked repositories, newest update first, 20 a page, each with its repository and whom it is assigned to; **All / Mine / Unassigned** filters it (GitHub: one search per 30 repositories; GitLab: each project read on its own, with a warning past 20). "Not found on this computer" is gone: Start on a repository whose folder Bobix does not know asks once, **Choose folder…** (its remotes are checked: https, ssh, `~/.ssh/config` aliases, every remote) or **Clone…**, and remembers it. The ticket flow works on GitHub issues too: **Open pull request…** pushes the branch and runs your own `gh pr create`; its checks are read with `gh pr view` / `gh pr checks`, and a red one gives **Copy Fix CI** with `gh` commands. The code can live in another repository than the issue (the issue's Addendum): the Start box's **Fix it in which project?** picks it (remembered per issue repository), the worktree, MR / PR and CI go there, the MR / PR closes the issue across repositories, and **Start in another project…** gives one issue a flow per repository it needs, all listed on the issue.
- **Habits become personal skills** ([#113](https://github.com/baonguyen-agilityio/bobix/issues/113), step 4 of the [product direction](product-direction.md)): Skills → From your habits. With Settings → Usage → "Read my prompts" and its own weekly scan switch on (both off by default), once a week Bobix gives the prompts of the last 14 days to Haiku through your own `claude -p` (no session saved, no hooks) and keeps only the kinds of request with their weekly counts. A kind asked in each of the last two weeks is suggested, with its evidence; when a skill like it exists, Bobix proposes improving yours (or using a plugin's) instead. Draft runs `claude -p` with Sonnet and the skill-creator, with the best sessions' prompts as examples; you can edit it, and only Approve writes `~/.claude/skills/<name>/SKILL.md`. Every change is a version with Undo; a skill Bobix made is offered an improvement only on evidence from its uses (follow-up prompts, fix requests, tokens per use) and removal after 30 days unused. Checked end to end on macOS on a scratch HOME with made-up sessions and real Haiku / Sonnet calls; the panel with made-up data in a browser (both themes, EN and VI). Not on Windows or Linux, nor by eye in the app window.
- **War room over Tailscale** ([#114](https://github.com/baonguyen-agilityio/bobix/issues/114), steps 5 and 6 of the [product direction](product-direction.md)): the Room tab. One room per problem. People chat freely; at the end the host's one summarizer (their own `claude -p`) arranges the chat into problem → options → pros and cons, the host edits that draft and decides. The creator's machine hosts it on a second port bound to its Tailscale address only; people are identified by `tailscale whois` and only those the host invited get in. Only typed or pasted messages cross, with common secret shapes redacted on both sides; every join, view, message, record and refusal is in the room's audit log. Deciding writes a self-contained HTML record on the host, and each guest writes the same record from the room's data. Headless `claude -p` can't publish an artifact, so the host gets "Copy for Claude" (with a warning) instead. Checked: unit and security tests, and two Bobix backends in two processes with their own data and real `tailscale whois` identity (chat → real AI draft → edit → decide → the same record on both), over loopback: macOS's firewall holds an unsigned test binary listening on the tailnet address until someone clicks Allow. ## 5. Known limits (by design or outside Bobix's control)

- Builds are not code-signed: macOS and Windows warn on first launch.
- Linux Wayland: through XWayland, Bobix sees the cursor only while it is on a pet, so fading near the cursor works only right next to a pet.
- Linux Wayland: no app may bring another app's window forward, so a click on a terminal session's pet opens it in the panel and names the terminal instead. Sessions in the Claude desktop app open directly, and a CLI in the Claude app's own terminal brings the app forward (not its terminal tab).
- Opening a session in the Claude desktop app uses `claude://code/continue`, not a documented API; it may change.
- While Bobix holds a permission request, Claude Code shows its own permission prompt in the terminal at the same time (checked with Claude Code 2.1.318), so an answer in either place goes through and a stuck Bobix never blocks Claude. Not checked: the Claude desktop app's own prompt, and older Claude Code versions.
- Approvals need the Node.js forwarder; with the curl / PowerShell fallback Bobix only watches.
- Linux installers are `.deb` only (Ubuntu, Debian). Other distributions aren't packaged.
- Only Claude Code sessions (terminal, IDE, the Code tab of the Claude app). Ordinary chats in the Claude app or on claude.ai have no hooks, so Bobix can't follow them.
  - Checked on 2026-11-04 on macOS while a chat answered: Claude desktop's logs (`~/Library/Logs/Claude`) record nothing about chats, and the only chat-related writes are to claude.ai's internal IndexedDB, which keep happening after the answer ends, so they can't serve as a status. Reading that database would mean reading private chat data in an undocumented format.
  - Not tried, decided against for now: reading the app's UI through the Accessibility API (e.g. whether a "Stop" button is showing; needs the Accessibility permission and breaks when the UI changes), and a browser extension for claude.ai on the web (does not cover the desktop app).
- To do column, issues and sessions:
  - A project gets New / Resume only once a session Bobix saw since it started used its repository; after Bobix restarts, a project is under "Not seen on this machine" until one of its sessions does something.
  - A start waits for its session until a new session there sends a first prompt that names the issue (#184); one you never send stays waiting. Cancel it with ✕ on the issue's start item (a Full start: Remove… on its flow). A Quick start's wait is kept in memory only: a Bobix restart drops it. A Full start waits again after a restart (#188).
  - A Full start whose session Claude opened in the repository's main folder relies on the prompt: it tells the session to work in the ticket's worktree. Bobix says where the session started, but can't move it.
  - Resume after a restart finds the session by its name in Claude desktop's session files (not a documented format). A session you rename yourself, or one named with a project code you changed since, is not found; the button says New again. Several sessions of one issue: Resume opens the one used last.
  - Several main sessions in one project folder share its files and can edit the same ones; Bobix doesn't prevent it. Side sessions Claude starts get their own worktree.
  - The same project path on two GitLabs counts as one project.
- Memory of the Tauri build is not measured yet (see section 2).
- Room needs a tailnet where laptops can reach each other; company tailnets that only allow user → server don't work yet (rc.7 release notes).
- Windows and Linux are tried by a person on a real machine, not by every release. What still fails there is listed here as it is found; macOS decides a release.
