# Privacy and security

Bobix runs entirely on your computer. It has no account and no analytics. Its only network request on its own asks GitHub, once a day, whether a newer version exists; you can turn that off. The panel can also read your GitLab issues, only if you turn it on (off by default).

> **Planned changes (not built yet).** Everything below is how Bobix works today. The [product direction](product-direction.md) plans to change some of it, each time with your consent and only when the matching step ships. Reading what you write in sessions is now an opt-in (step 1, below: off by default, counts only). The skills audit (step 2, below) may move your skills and edit a project's `CLAUDE.md`, only when you click, with a backup and an undo. Habits become skills (step 4, below) asks Haiku through your own `claude -p` once a week, only with two switches on, and writes to `~/.claude/skills` only when you approve. Still planned: a war room adds a port on your Tailscale network. This page will change with each of them.

## What it reads

| Source | What | Why |
|--------|------|-----|
| Claude Code hook events | session id, project folder, your prompt, tool name and its path / command / pattern, permission requests, the claude process id, and in the Claude desktop app its session id | to show what each session is doing and open it on click |
| The Claude desktop app's session file for a session it runs (`…/Claude/claude-code-sessions/…/<id>.json`) | only `spawnedFrom.sessionId`, the session it was started from; while GitLab is on, also each session's title, folder, last activity and whether it is archived | to show side sessions next to their parent, and to find the session you started from an issue (by its name) for Resume |
| The session's git repository, with `git` (local only, no fetch) | branch, upstream and ahead / behind, the number of changed files, commits on no remote, the last commit's subject and time, the number of worktrees, the remote URLs | the Git part of a session's details, and (GitLab on) which GitLab project and issue it works on. Remote URLs stay in the app's main process and are never shown or sent: they can hold credentials. |
| The session transcript (`~/.claude/projects/…jsonl`) | the last ~512 KB (and the first 256 KB, for the title): the final answer, token usage, the session title | the "report" line, the context meter, the pet's name |
| The same transcript and its subagents' files (`…/<session>/subagents/*.jsonl`), every 5 s, only what was added since the last read | for each answer: the model, the usage fields (input, output, cache write and cache read tokens), the time of each line, and the names of the tools it called. Not the text of prompts or answers. The file is the one Claude names in its hook events, so it is found the same way on macOS, Windows and Linux, and in the CLI and the Claude desktop app (both write it there; checked on macOS). | **Usage** on the Overview, in a session's details and on the pet card: tokens, model mix, active time, how much is re-reading context, the size against your usual session, an API-equivalent estimate and three warnings (session too long, a heavy model on light work, read-only exploration on a heavy model) |
| Only while Settings → Usage → "Read my prompts to count them by kind" is on (**off by default**): in the same files, your prompts and the shell commands Claude runs | each prompt becomes one kind (question, fix, review, docs, building, other) by its words, and each command whether it only reads (`cat`, `grep`, `git log`…). The text is dropped at once; only the counts are kept | the counts in a session's details, and better warnings (a question on a heavy model, `grep` in the shell as exploration) |
| Your past transcripts in the same `projects` folder, once per app start | the same fields as above, for the newest 40 sessions of the last 30 days that Bobix has not counted yet and that are not live | your "usual session": the median, by API-equivalent price, of your past sessions of 10 turns or more |
| Skills audit (only when you open it): your skills (`~/.claude/skills`, the project's `.claude/skills`, the enabled plugins' and claude.ai's, as listed in [skill-process.md](skill-process.md)) and every transcript under `~/.claude/projects` modified in the last 30 days, with their subagents' files | of each skill: its name, folder and the size of its description. Of the transcripts, only lines that call the Skill tool: the skill's name and the time. With "Read my prompts" on, also the name of each `/command` you typed. No other text is kept, and nothing is written | which skills you used in the last 30 days, which you did not, and which are duplicates |
| Habits become skills (Skills → From your habits), only while both Settings → Usage → "Read my prompts to count them by kind" and "the weekly scan" there are on (**both off by default**): every transcript under `~/.claude/projects` modified in the last 30 days (not the subagents' files) | the prompts you typed in the last 14 days, and, for each skill Bobix made or changed, its uses and what followed them (the prompts you typed after it, whether they ask for a fix, the tokens spent) | once a week, to find the kinds of request you make every week (below: they go to Haiku), and the evidence an improvement needs. The prompts are held in memory for the scan only; Bobix keeps each kind's short label and summary as Haiku wrote them, its counts per week and the session ids, and the numbers per skill |

The hook script drops file contents and tool output before sending anything. All of this is kept **in memory only** and forgotten when a session ends or the app quits, except a finished session's usage numbers (`usage.json`, below).

Usage never uses your Claude login: Bobix reads no credential, calls no account or quota API and writes nothing to Claude's files. The real 5-hour and weekly limits of a subscription are only in Claude's own `/usage`; the dollar figure is an estimate at public API prices (a switch in Settings hides it).

## What it sends, and to whom

- **Nothing about you or your sessions leaves your computer**, unless you send feedback yourself (below). Fonts and images are bundled.
- **New version check** (Settings → "Tell me about new versions", on by default): once a day the app reads `https://api.github.com/repos/baonguyen-agilityio/bobix/releases/latest`, GitHub's public page of the latest release. It sends no data, only the request itself, so GitHub sees what any web page sees: your IP address and `Bobix/<version>` as the program name. No account or token is used.
- **Feedback** (Settings → Feedback in the panel, or the tray menu, only when you use it): opens GitHub's new-issue form in your browser with your text filled in. Nothing is sent until you submit it there, with your GitHub account, and the issue is public. A bug report also fills in technical details: the app version, operating system, hook state, some settings, session states and recent errors with folders and tokens removed. You can read them before opening the form. No prompts, code, project names or tokens. An idea carries no technical details.
- **GitLab issues** (Settings → Work (GitLab, GitHub): "Show my GitLab issues", **off by default**): while the switch is on, Bobix runs your own `glab auth status` to learn which GitLab hosts you are signed in to (it reads only the "Logged in to <host> as" lines; glab masks the token there), then for each of them `glab api --hostname <host> issues?scope=assigned_to_me&state=opened&per_page=100` when you turn it on, when the app starts, every 5 minutes and when you press Refresh. That is one read (GET) per host of the open issues assigned to you. With it, two more reads per host: `merge_requests?scope=created_by_me&state=opened&per_page=100` (your open merge requests: an issue one of them closes, by "Closes #n" in its description or a branch named `<n>-…`, waits for review) and `issues?scope=assigned_to_me&state=closed&updated_after=<4 days ago>&per_page=100` (the board keeps those closed today, for "Done today" and the report, and those closed on the last working day, for the stand-up). When a session here works on an issue that is not assigned to you (its branch `<n>-…` or its start names it), Bobix reads that one issue too (`projects/<project>/issues/<n>`, a GET, once per issue, at most 10 per read) so the session shows under its ticket; it drops it once no session works on it or it is closed. Bobix never writes to GitLab. `glab` uses the sign-in you made yourself (`glab auth login --hostname <host>`); Bobix never signs in for you, never reads or stores the token, and sends nothing about your prompts, sessions or code, only that request. It keeps the issues' number, title, project, labels, due date and link in memory. Off, Bobix makes no GitLab request at all. Links open in your browser, and only links of the issues it read.
- **GitHub issues** (Settings → Work (GitLab, GitHub): "Show my GitHub issues", **off by default**): the same, through your own `gh`. Bobix runs `gh auth status` to learn which GitHub hosts (github.com, GitHub Enterprise) you are signed in to; it reads only the "Logged in to <host> account <name>" lines and the "Active account" line after each (gh masks the token there), so with several accounts on one host it uses the active one, as `gh` itself does. Then for each host `gh api --hostname <host> issues?filter=assigned&state=open&per_page=100`, at the same times as GitLab: one read (GET) per host of the open issues assigned to you; pull requests in that answer are dropped. With it, `gh api --hostname <host> graphql` with a query (no mutation) for your open pull requests and the issues each one closes, and `issues?filter=assigned&state=closed&since=<4 days ago>&per_page=100` for the issues closed today and on the last working day, and `repos/<owner>/<repo>/issues/<n>` for an issue a session here works on that is not assigned to you (as for GitLab above). It keeps a pull request's link and the issue numbers it closes. Bobix never writes to GitHub, never signs in for you (`gh auth login`), never reads or stores the token, and keeps the same fields in memory (no due date: GitHub issues have none). Off, Bobix makes no request through gh at all.
- **Habits become skills** (only while both switches above are on): once a week, and when you press Scan now, Bobix runs your own `claude -p` with Haiku and gives it the prompts you typed in the last 14 days (the newest 300, each cut at 400 characters), so they go to Anthropic under your own Claude sign-in, as any prompt you send Claude does. When you press Draft, it runs `claude -p` with Sonnet and gives it the kind of request, up to three prompts from each of the kind's best sessions, and, for an improvement, the skill as it is and the prompts you typed after using it. Bobix never reads your Claude credentials; `claude` uses its own sign-in.
- Hooks talk to the app over `127.0.0.1` only. The server checks the Host header (blocks DNS rebinding) and requires the per-user token on every event and on the state stream, so web pages and other users on the same machine can neither feed it nor read it.
- **Notifications** show a session's request or the start of its final answer through your operating system. They can appear while you share your screen; turn them off or use **Pause notifications** in Settings.

## What it runs

- `node ~/.claude/bobix/hook.js <port>` on each Claude Code hook event, in the background so Claude never waits for it. SessionStart runs in the foreground (5 s at most, a local call) so it can name a session started from an issue; Claude lets you type meanwhile. The one exception is a permission request: there the hook waits for your answer in Bobix (Settings → "Approve from Bobix": by default until you answer there, or a time limit you set; off if you choose). Claude Code shows its own prompt in the terminal at the same time, so you can answer there instead. Runs without a person at Bobix (`claude -p`, Agent SDK apps) never wait. Answers come only from Bobix's own windows and notifications, never over the network. Fallbacks without Node.js: `curl` or PowerShell (no approvals).
- When you click a pet: `open -a <app>` (macOS), `WScript.Shell.AppActivate` via PowerShell (Windows) or `xdotool` (Linux) to bring the session's window forward, and `ps` / `Get-CimInstance` to find that window's process. In the Claude desktop app it opens `claude://code/continue?session=<id>`, a link that app registers. It is not a documented public API and may change; if it stops working, the click falls back to the session's details.
- For each folder a session works in, at most every 30 s (and on a session's start and end): `git status --porcelain=v2 --branch`, `git rev-parse --show-toplevel`, `git log -1`, `git rev-list --count HEAD --not --remotes`, `git worktree list --porcelain`, `git remote -v`. Read-only, without taking git's index lock; nothing is fetched or pushed.
- Only while GitLab is on: `glab auth status` and `glab api …` as above, and once a login shell (`command -v glab`) to find where glab is installed. The same for GitHub with `gh` while GitHub is on.
- **Start** on an issue under Sessions → To do in the panel (only when you press it): reads that issue once more through your own `glab` / `gh` (`glab api --hostname <host> projects/<project>/issues/<number>` or `gh api --hostname <host> repos/<owner>/<repo>/issues/<number>`, a GET) for its description, and shows the prompt (title, description cut at 3000 characters, link) in a box you can edit. Bobix keeps none of it. **Open session and copy prompt** copies the prompt to your clipboard and opens `claude://code/new?folder=<the project's folder>&q=<the prompt>`, Claude's [documented link](https://support.claude.com/en/articles/14729294-open-claude-desktop-with-a-link) for a new session with its prompt box filled in (the Claude app asks you to confirm the folder; nothing is sent until you press Enter there). The prompt goes only to the Claude app on this computer.
- **Skills in the Start box** (only when you press Start): Bobix lists the Claude Code skills a session in that folder can call, to suggest one. It reads only the `name`, `description` and `user-invocable` lines at the top of each `SKILL.md` in the places Claude Code keeps skills: `~/.claude/skills` (yours, and `synced/` from your claude.ai account), `.claude/skills` in the folder and its parents up to the repository root, the managed folder your organization may deploy (`/Library/Application Support/ClaudeCode` on macOS, `/etc/claude-code` on Linux, `C:\Program Files\ClaudeCode` on Windows), and the plugins in `~/.claude/plugins/installed_plugins.json` that are installed for you or for that folder and enabled (`enabledPlugins` in `~/.claude/settings.json`, the folder's `.claude/settings.json` and `.claude/settings.local.json`). Nothing is copied, kept or changed. Your role and the skills you pin (both in the **Skills** tab; your own skills are read the same way from your own skill folders and plugins) are kept in Bobix's settings. The Skills tab also lists, per project on this machine, the project's and team's skills in its folder, read the same way when you open the tab.
- **Skill process** (only when you press Start, or open the Skills screen): Bobix reads `.bobix/skills.json` at the root of the project's repository, if there is one ([format](skill-process.md)). It never writes it. A process you import in the Skills screen (per project) is read from the file you choose, or from an `https://` link when you press Import: one GET with your system's `curl`, https only, 64 KB and 10 s at most. It is kept in Bobix's settings for that project. Process files are data only. Bobix checks them strictly and runs nothing in them. For a skill the process names that Claude doesn't have, Bobix only shows a line to copy; it never installs anything, and writes to Claude's skill folders only when you click Disable or Remove in the skills audit (above). The first session then created in that folder (SessionStart with source `startup`) is linked to the issue, and Bobix's SessionStart hook answers with its name (`[<code>-<number>] <short title>`, as `/rename` would set it); this is the only hook output besides permission answers. Until then the issue shows "waiting for a new session" with ✕ to cancel. **Resume** does what a click on the session's pet does, or, for a session Bobix doesn't see running, opens `claude://code/continue?session=<id>` for the newest Claude desktop session in that folder with the issue's name.
- **Habits become skills**: `claude -p --model haiku|sonnet --output-format text --no-session-persistence --strict-mcp-config --settings {"disableAllHooks":true} --tools <none, or Skill,Read for a draft>`, the prompt on its standard input, in the app's settings folder → `habit-skills/work`, found the way your shell finds `claude` (a login shell's `command -v claude`). No session is saved, no hook (Bobix's own included) and no MCP server runs, and Claude's settings files are not written. A scan gives up after 3 minutes, a draft after 7.
- Arguments are always passed as lists, never through a shell.

## Your organization's policies

Bobix only uses Claude Code's documented hooks. If your organization's managed settings allow only managed hooks (`allowManagedHooksOnly`), Claude Code does not run Bobix's hooks and the app receives nothing. Bobix does not try to work around that.
