# Privacy and security

Bobix runs on your computer. It has no account and no analytics, and nothing goes to Bobix's author. By default it makes two kinds of request: once a day it reads GitHub's update list to see whether a newer version exists (you can turn that off; it downloads a new version only when you press Update), and the panel reads the open issues of the GitLab and GitHub repositories you pick, through your own `glab` and `gh`, wherever you signed them in (on by default; one switch each turns it off, below). Text goes to Anthropic only for the features you switch on or press (the weekly habits scan, the ticket helper, the war room draft: below), through your own `claude -p` and your own Claude sign-in, as any prompt you send Claude does. While you host a war room, the people you invite reach that room over your Tailscale network (below).

> **What is built.** Everything below is how Bobix works today, including the parts that arrived in the 0.2 test builds: usage per session, the skills audit and model rules, the ticket flow under Work, habits into skills and the war room. Each one asks before it does anything that reaches beyond reading: reading what you write in sessions is off by default (counts only); the skills audit may move your skills and edit a project's `CLAUDE.md` only when you click, with a backup and an undo; habits into skills asks Haiku through your own `claude -p` once a week, only with two switches on, and writes to `~/.claude/skills` only when you approve; the war room opens a second port, on your Tailscale address only, while you host a room. The [product direction](product-direction.md) records why.

| The same transcript and its subagents' files (`…/<session>/subagents/*.jsonl`), every 5 s, only what was added since the last read | for each answer: the model, the usage fields (input, output, cache write and cache read tokens), the time of each line, and the names of the tools it called. | Skills audit (only when you open it): your skills (`~/.claude/skills`, the project's `.claude/skills`, the enabled plugins' and claude.ai's, as listed in [skill-process.md](skill-process.md)) and every transcript under `~/.claude/projects` modified in the last 30 days, with their subagents' files | of each skill: its name, folder and the size of its description. Of the transcripts, only lines that call the Skill tool: the skill's name and the time. With "Read my prompts" on, also the name of each `/command` you typed. No other text is kept, and nothing is written | which skills you used in the last 30 days, which you did not, and which are duplicates |
| A ticket's work log (Work, only for a ticket you started there): `.bobix-log/work-log.md` in its worktree, on each hook event of its session | its status, the ticket as the session restated it, its questions and your answers, what was put off, the plan and its mapping, steps, assumptions and result, as the session wrote them | the Work screen, the session's details, and the mark on the pet when a new assumption appears |
| The Markdown files a ticket flow's plan names (phone access only, when that plan is held for approval and a phone with the right to approve plans is paired): the `.md` files whose names the plan text itself holds, that really lie inside the session's folder | up to 8 such files, at most 8 KB of text each and 48 KB together, read once when the plan is held | so the phone shows what Approve covers (see Phone access below) |
| Habits become skills (Skills → From your habits), only while both Settings → Usage → "Read my prompts to count them by kind" and "the weekly scan" there are on (**both off by default**): every transcript under `~/.claude/projects` modified in the last 30 days (not the subagents' files) | the prompts you typed in the last 14 days, and, for each skill Bobix made or changed, its uses and what followed them (the prompts you typed after it, whether they ask for a fix, the tokens spent) | once a week, to find the kinds of request you make every week (below: they go to Haiku), and the evidence an improvement needs. The prompts are held in memory for the scan only; Bobix keeps each kind's short label and summary as Haiku wrote them, its counts per week and the session ids, and the numbers per skill |

The hook script drops file contents and tool output before sending anything. All of this is kept **in memory only** and forgotten when a session ends or the app quits, except a finished session's usage numbers (`usage.json`, below) and, in memory only until the app quits, the id, Claude desktop session id and folder of the last 50 sessions that ended, so Open can still reopen them.

Usage never uses your Claude login: Bobix reads no credential, calls no account or quota API and writes nothing to Claude's files. The real 5-hour and weekly limits of a subscription are only in Claude's own `/usage`; the dollar figure is an estimate at public API prices (a switch in Settings hides it).

## What it sends, and to whom

- **Nothing goes to Bobix's author or to any server of Bobix.** What leaves your computer goes only where this section says: GitHub's update list and, when you press Update, the update file, the issue reads through your own `glab` / `gh`, feedback you submit yourself, and the `claude -p` calls of the features you switch on or press, which go to Anthropic under your own Claude sign-in (the weekly habits scan and draft, the ticket helper, the war room draft). Only when you click, Bobix also runs your own `git` and `glab` / `gh` against your own remotes: **Prepare start** lists the remote's branches (`git ls-remote`) and a Full Start fetches the branch you picked (`git fetch`), **Push and open MR / pull request** pushes the ticket's branch and creates it, and a skill process imported from an `https://` link is one GET with your system's `curl`. Each is described below. Fonts and images are bundled.
- **New version check** (Settings → "Tell me about new versions", on by default; Settings → App → Updates → **Check now** does the same when you press it, even with the switch off): once a day the app reads one small JSON file from GitHub: `https://github.com/baonguyen-agilityio/bobix/releases/latest/download/latest.json`, the update list of the latest stable release, or, only while Settings → **Get test builds** is on (off by default), `https://github.com/baonguyen-agilityio/bobix/releases/download/test-channel/test.json`. GitHub redirects the request to its file host. The request carries no data about you or your sessions: GitHub sees what any web page sees (your IP address) and the program name `tauri-plugin-updater/<its version>`. No account or token is used. The list names the newest version and where its files are.
- **Updating** (only when you press **Update**, in Settings, the tray menu or a notification): the app downloads the update file for your system from the same release on `github.com` (the same file as the installer on Windows and Linux), checks its signature against the public key built into the app, and only then installs it. A file that fails the check is never installed. Nothing is sent but the download request itself. On Linux the package manager asks for your password; on macOS an app installed where only an administrator can write asks for it too. Before the restart Bobix tells you about held permission requests and running ticket flows, and the held requests go back to Claude's own prompt.
- **Feedback** (Settings → Feedback in the panel, or the tray menu, only when you use it): opens GitHub's new-issue form in your browser with your text filled in. Nothing is sent until you submit it there, with your GitHub account, and the issue is public. A bug report also fills in technical details: the app version, operating system, hook state, some settings, session states and recent errors with folders and tokens removed. You can read them before opening the form. No prompts, code, project names or tokens. An idea carries no technical details.
- **GitLab issues** (Settings → Work (GitLab, GitHub): "GitLab issues", **on by default**; it reads only where your own glab is signed in): Bobix runs your own `glab auth status` to learn which GitLab hosts you are signed in to, and as whom (it reads only the "Logged in to <host> as <name>" lines; glab masks the token there; the name tells which issues are assigned to you). The first time a host is read, `glab api --hostname <host> projects?membership=true&simple=true&order_by=last_activity_at&per_page=100` (up to 5 pages) lists the projects you are a member of, and the ones active in the last 90 days are ticked. The ticks are kept in Bobix's settings (`workRepos`); you change them in Work → Repos to list, which reads that list again when you open it (and on **Read again**). Then, when the app starts, every 5 minutes, when you press Refresh and when you change the filter or the page: for each ticked project, `projects/<project>/issues?state=opened&order_by=updated_at&sort=desc&per_page=<n>&page=<p>` (with `scope=assigned_to_me` for **Mine**, `assignee_id=None` for **Unassigned**), one read (GET) per project, as many issues as the page shown needs plus one. With more than 20 projects ticked, Work warns and suggests unticking some. With it, two more reads per host: `merge_requests?scope=created_by_me&state=opened&per_page=100` (your open merge requests: an issue one of them closes, by "Closes #n" in its description or a branch named `<n>-…`, waits for review) and `issues?scope=assigned_to_me&state=closed&updated_after=<4 days ago>&per_page=100` (the board keeps those closed today, for "Done today" and the report, and those closed on the last working day, for the stand-up). When a session here works on an issue that is not in the list (its branch `<n>-…` or its start names it), Bobix reads that one issue too (`projects/<project>/issues/<n>`, a GET, once per issue, at most 10 per read) so the session shows under its ticket; it drops it once no session works on it or it is closed. Bobix writes to GitLab only when you press **Push and open MR** on a ticket (below). `glab` uses the sign-in you made yourself (`glab auth login --hostname <host>`); Bobix never signs in for you, never reads or stores the token, and sends nothing about your prompts, sessions or code, only those requests. It keeps the issues' number, title, project, labels, due date, assignees' names, last update and link in memory, and the list of projects for the picker. Off, Bobix makes no GitLab request at all. Links open in your browser, and only links of the issues it read.
- **GitHub issues** (Settings → Work (GitLab, GitHub): "GitHub issues", **on by default**; it reads only where your own gh is signed in): the same, through your own `gh`. Bobix runs `gh auth status` to learn which GitHub hosts (github.com, GitHub Enterprise) you are signed in to; it reads only the "Logged in to <host> account <name>" lines and the "Active account" line after each (gh masks the token there), so with several accounts on one host it uses the active one, as `gh` itself does, and that name tells which issues are yours. The first time a host is read, `gh api --hostname <host> user/repos?per_page=100&sort=pushed` (up to 5 pages: the repositories you own, collaborate on or reach through an organization) gives the picker's list and the first ticks (active in the last 90 days). The issues of the ticked repositories, at the same times as GitLab's: `gh api --hostname <host> -X GET search/issues -f q="is:issue is:open repo:<owner>/<repo> …" -f sort=updated -f order=desc -f per_page=<n> -f page=<p>` (with `assignee:@me` for **Mine**, `no:assignee` for **Unassigned**), one search (GET) per 30 ticked repositories. With it, `gh api --hostname <host> graphql` with a query (no mutation) for your open pull requests and the issues each one closes, `issues?filter=assigned&state=closed&since=<4 days ago>&per_page=100` for the issues closed today and on the last working day, and `repos/<owner>/<repo>/issues/<n>` for an issue a session here works on that is not in the list (as for GitLab above). It keeps a pull request's link and the issue numbers it closes. Bobix writes to GitHub only when you press **Push and open pull request** on a ticket (below). It never signs in for you (`gh auth login`), never reads or stores the token, and keeps the same fields in memory (no due date: GitHub issues have none). Off, Bobix makes no request through gh at all.
- Both switches used to be off by default. Settings from a Bobix before the repo picker turn both on once, as on a new install; each still reads only where its CLI is signed in, and a switch you turn off after that stays off.
- **Habits become skills** (only while Settings → Usage → "Read my prompts to count them by kind" and "the weekly scan" are both on; both are off by default): once a week, and when you press Scan now, Bobix runs your own `claude -p` with Haiku and gives it the prompts you typed in the last 14 days (the newest 300, each cut at 400 characters), so they go to Anthropic under your own Claude sign-in, as any prompt you send Claude does. When you press Draft, it runs `claude -p` with Sonnet and gives it the kind of request, up to three prompts from each of the kind's best sessions, and, for an improvement, the skill file as it is (your own `~/.claude/skills/<name>/SKILL.md`, or an existing similar skill's when a new one is drafted) and the prompts you typed after using it. A draft lets Claude use its `Skill` and `Read` tools: the prompt asks only for the skill, but Claude may read files on this computer, and what it reads goes to Anthropic in that conversation. Bobix never reads your Claude credentials; `claude` uses its own sign-in.
- **War room** (the Room tab, only when you create or join a room). Hosting: while you host a room that is not decided yet, Bobix listens on a second port (4748), bound to this computer's Tailscale address only (`tailscale ip -4`), never on all interfaces. The panel's own server stays on `127.0.0.1` with its token. A request is answered only if it comes from a Tailscale address, carries Bobix's room header with this address as its Host (so a web page can't reach it), and its sender's login (`tailscale whois`) is one you invited to that room; anyone else gets a refusal, which the audit log records. What crosses that port: the room as you and your guests typed it (title, problem, the chat messages with who sent them and when, the draft of the record, the decision, the invited logins and the people's names and device names). Each guest writes the decision record itself from that, never from HTML the host sends. What never does: transcripts, logs, session data or anything else from this computer. Joining: Bobix sends the host only the messages you type or paste into the room (`{ text }`). Before anything is sent, and again when the host stores it, common secret shapes (private keys, GitHub / GitLab / Slack / OpenAI / Anthropic / AWS / Google tokens, JWTs, `Bearer …`, passwords in URLs, `password=` / `token:` and similar) are replaced by `[redacted]`; this catches common shapes, not every possible secret, so don't paste one. The draft: when the host presses Draft, only the host's own `claude -p` (Sonnet), on the host's computer, reads the chat once and arranges it into problem, options, pros and cons (no session saved, no hooks, no MCP servers, no tools). The chat goes to Anthropic under the host's own Claude sign-in, as any prompt does; guests' Claude accounts never see it. The host edits that draft and decides. **Copy for Claude** (host only, after a warning) copies the record's text so you can paste it into claude.ai yourself: Claude's command line has no way to publish an artifact. The first time you host a room, macOS may ask once whether Bobix may accept incoming connections (builds that are not signed are not allowed on their own): allow it, or invited people can't reach the room; the Room tab says so too.
- Hooks talk to the app over `127.0.0.1` only. The server checks the Host header (blocks DNS rebinding) and requires the per-user token on every event and on the state stream, so web pages and other users on the same machine can neither feed it nor read it.
- **Ticket flow, Haiku** (Work, only when you click **Ask Haiku to propose** or **Fill gaps with Haiku**): Bobix runs your own `claude -p` with Haiku, with the issue's title and description (cut at 3000 characters) to propose a split and models, or with the work log, the branch's commit subjects and its changed-file list to sum up what the log leaves out. They go to Anthropic under your own Claude sign-in, as any prompt you send Claude does. Nothing else is sent; the work log itself is never shared.
- **Phone access** (Settings → Phones; **still in development: in no stable release, `-rc` test build or `develop` build; present only in a `-phones` pre-release (invited testers, installed by hand, never offered by the update check) or a build made with the `phones` Cargo feature**; **off by default**). Switched off and never used, nothing happens: no connection, no key, no file, no thread (a build without the feature does not even contain the section). Switched on, the computer holds **one outbound connection to the relay whose address you typed** (`wss://`; a build with phone access also takes a plain `ws://` address on a private network, for trying it at home: then the relay's own frames, such as device ids, the lists of peers and grants, presence, push and grant frames and the timing and size of packets, travel **in clear** on that network, though the contents stay sealed end to end; a private address is not a trusted network, and on hotel, café or office Wi-Fi someone on it could pose as the relay and watch or block the traffic, so use `wss://` there) (Bobix has no built-in one) and sends nothing else for this feature. Over it go, each sealed on this computer for one paired phone (XChaCha20-Poly1305; the relay holds no key that opens a packet): the list of your sessions (a title, the project folder's name, the state, a pet colour), what waits (only the kind of item (request, plan or question), a preview of at most 300 bytes, whether it was cut or looks destructive and the seconds left; **the tool's name is not sent**), the notices ("a request waits", "a session finished"), the result of a command, and, only when a phone with the matching right asks for it, the whole input of one held request, plan or question (with its options), or a session's last 40 lines without your prompts (the tools it ran and Claude's own replies, redacted and without hidden characters). **A phone with the Start right can also ask for the preview of a ticket's start: that is the whole prompt the ticket would start with, including the issue's title and body as read from your tracker, the project, whether its folder is known here and the free disk space. That prompt is sent as it is (not passed through the redactor), and it is the largest piece of text that can leave the computer; leave "Start tickets" unticked (the default) for a phone that should not get it.** Every preview, notice and list line passes the secret redactor and loses hidden characters; the whole input is not redacted but is shown with hidden characters as visible escapes and a warning on a destructive one. Never sent: the transcript path, the prompts you typed in your sessions, git remotes, usage. **The relay sees** device ids, which device sends to which, packet sizes and times, the push tokens a phone registers, whether each device is online, offline or asleep, and a client's network address while it is connected; it keeps a packet for an offline device at most 10 minutes. **Invite codes** (a relay that serves invited computers only): a code the relay's owner makes on their computer carries that computer's public key, the relay's id, a random nonce, an expiry and the label the owner typed, so whoever has the code sees those; the computer keeps no copy. When a computer enters a code, the relay keeps on its disk that computer's device id with the label, which owner's code it was and when, until an owner removes it, and the code's nonce until the code would have expired. An owner's computer is shown that list (ids, labels, dates) by the relay; nothing about invitations is stored on any computer. The relay's log (standard output, and the daily files when `LOG_DIR` is set, 14 days) also notes each admission and removal by device ids only: "<id> invited by a code of <owner id>" and "<id> no longer invited (removed by <owner id>)". A push notification reaches the phone through Apple's or Google's service carrying only the same sealed packet and generic text keys, so those services cannot read the request either. **On this computer:** the device's keys and the key that seals the list of phones are two entries (`identity`, `phones-seal`) under the service name `Bobix` in the system keychain, or an owner-only file under `secrets/` in the data folder where there is no keychain or `BOBIX_DATA_DIR` is set (a test run never touches the keychain); `phones.sealed` (the list of phones, sealed), `phones.json` (the switch, the relay address, the choices below), the packet counters, the results of the last 24 hours and a log of the last 300 remote commands (who, what, outcome; never the input) are files in the data folder. **A phone can do only what you ticked** when you confirmed its pairing or later in Settings → Phones (answer a request, approve a plan, answer a question, start a ticket, stop a waiting session, see session activity; starting and stopping start unticked) and only after that confirmation. **While the pets are hidden or paused**, a request that nothing here would show is **held for your phones** when nobody has used the keyboard or mouse for 10 seconds (read from the system without a permission prompt, once a second, only while such a request waits; where it cannot be read, "keep requests for my phone / let Claude ask at the computer" in Settings decides); Claude's own prompt stays available, and the first answer, there or on a phone, wins. The hook that holds such a request waits as long as your wait setting says (no longer cut at 5 minutes), and without a limit for a request held for phones. Each phone is told Stop is possible only for a session where it holds both the Answer and the Stop right. "Keep this computer awake" (off by default) holds the computer awake while a session works or waits and phone access is on. Turning the switch off disconnects every phone; disconnecting one cuts it at once and the relay is told.
- **Plan files** (phone access, a ticket flow's plan held for approval): the plan text may name other Markdown files (`phase-01.md`); when it does, the computer reads them **once, when the plan is held**, so a phone approves exactly what it was shown, and seals them into that plan's `detail` for a phone that holds the right to approve plans. To no other phone and in no other message: not in the list of sessions, the previews, the notices or the push (which never carry a file's name or text). **Which files**: only a name that the plan text itself holds and that ends in `.md`; it is resolved on the computer with every symbolic link followed and every `..` removed, and the file it reaches must lie inside the session's folder (the folder Claude Code reports for the session: for a ticket flow, the folder it runs in, normally its worktree), be an ordinary file (never a folder, a device or a pipe, which is not even opened) and still end in `.md`. A name that leads outside the folder, a link inside the folder that points outside it, an absolute path elsewhere and a file that is not Markdown are refused: nothing of them is read or listed. A link inside the folder that points to a file inside it is read, as that file. **How much**: at most 8 files in the order the plan names them, at most 8 KB of text from each (a longer file is sent shortened to a line end, and marked so) and 48 KB for all of them (a file that does not fit, one larger than 48 KB, one that cannot be opened and one that is not text (not UTF-8, or with a NUL) is listed by name, folder and size only, with no text). Each file's text passes the secret redactor (which also removes control characters, other than line ends and tabs) and has its other hidden characters written as visible escapes, as the previews do (the plan text itself is not redacted, as the whole input of a request is not); its name and folder, as the project's own relative path, with hidden characters escaped. **What the phone does with it**: it shows the files read only, and **cannot approve** a plan with a file that is shortened or only listed (the computer refuses that Approve itself); Send back always works. The files stay in the computer's memory while the plan is held and on the phone's screen while it is open; the phone does not keep a detail, and the computer writes none of this to disk.
- **Notifications** show a session's request or the start of its final answer through your operating system. They can appear while you share your screen; turn them off or use **Pause notifications** in Settings.
- **Phone notifications on iOS** (the phone app only, once it is paired and you allowed notifications): the computer seals each notice with the phone's key, so the relay and Apple carry ciphertext, a push type, a priority and the phone's push token; neither can read a project name or a command. The phone's notification service extension opens the notice on the phone with the `box` key from the shared keychain group, writes the text the computer already redacted (token-shaped strings are replaced before anything leaves the computer), and does nothing else: no network call, no signing key. The phone's signing key lives in a keychain group only the app lists, and pairing again moves one an earlier build left in the shared group out of it. **Hide details** (Settings, off by default) makes it write only "A session needs you", also on the lock screen; the tap still opens the right request. A notice that cannot be opened, was already seen or is too old shows that generic text (never the relay's own words) and changes nothing else; an alert sent without `mutable-content` starts no extension, so iOS shows the relay's text for it, which is the one case this cannot cover. With Hide details on, the shared list keeps no session or project names, and Disconnect, Erase and a revoke remove the notifications still shown, on iOS and Android. The extension and the app share one small file in the app's App Group (the receive counters of each paired computer and the Hide details switch); it holds no key, is kept out of backups, and a push that arrives twice never ends a pairing.
- **Phone notifications on Android** (the phone app only, once it is paired and you allowed notifications; the build needs a Firebase project, which is the owner's step and not set up yet): the notice travels as an FCM data message carrying the same sealed packet, so Google and the relay see ciphertext, a push type, a priority and the phone's push token (and Firebase's installation id), not a project name or a command. The app fetches that token only after pairing, Firebase analytics is switched off in the manifest, and the push service opens the notice with the `box` key, posts it in the "Needs you" channel (private on the lock screen, with a public version that says only "A session needs you"). **Hide details** makes every notification generic.
- **Android widgets, Live Update and Quick Settings tiles** (the phone app, once paired): the phone app writes a list of what the widgets and tiles show to `surfaces/list.json` and the pets' pictures beside it, in the app's private no-backup files. The list holds session names, project names, counts, pet states, and the computer's name and whether it is reachable. Three home screen widgets and two Quick Settings tiles (Bobix, Start) read it; the Live Update (a pinned notification while a session waits, promoted on Android 16 and later, an ordinary ongoing notification before) is private on the lock screen, which says only that one waits, unless the phone shows all notification content and **Hide details** is off, in which case the first session's name shows. **Hide details** also keeps session names off the widgets and tiles. Content older than 15 minutes (or than the seconds the computer still holds the request, if less) is drawn dimmed as "Updated hh:mm" and never says that something needs you. Every tap opens the app only; nothing is answered from a widget, a tile or the notification. Disconnecting clears the list and the pictures.
- **What the phone keeps** (the phone app, iOS and Android): three keys. `auth` (logs in to the relay) and `box` (opens what the computer sealed) are kept on this device only, never in a backup or iCloud Keychain, and need no biometrics; `sign` (signs each command) is an ECDSA P-256 key in the Secure Enclave on iOS and in the Android Keystore (StrongBox where the phone has it), never leaves that hardware and asks for Face ID or a fingerprint on **every** command, Deny included. The biometric step protects the signing key, and it assumes the app itself is intact: a phone that is rooted or jailbroken, or an app that has been altered, is outside what it can promise. Two small files in the app's private folder, which no backup contains: `link-state.json` (the paired computer's name, its relay address, the rights you gave this phone, the packet counters, the last `home` the computer sent with the time it came, and the ids, never the content, of commands sent whose results have not come) and `app-settings.json` (theme, language, and whether the app asks to unlock). The whole input of a request, a plan, or a session's last lines is held in memory while a screen shows it and is never written. Nothing is queued: with no network or no relay, sending is off. "Require Face ID / fingerprint to open" is on by default and the app switcher shows a plain cover instead of the content. **Disconnect** (or "Erase and pair again", or the computer telling the phone it was revoked) tells the computer when the phone is connected, then erases the three keys, `link-state.json`, the file the widgets read and ends any Live Activity; reinstalling the app also erases any key an earlier install left. **Send feedback** only opens GitHub's new-issue form in the phone's browser, filled with redacted facts you can read first; nothing is sent until you submit it there.
- **Phone widgets, Live Activity and controls on iOS** (the phone app only): the app and the notification extension write a small file in the app's App Group with the names of the sessions, the project, a pet's state, counts and the computer's name and state (no command, no tool input, no key); the widgets, the Live Activity and the controls read it. It can show on the Lock Screen, so **Hide details** (Settings) makes those show counts only. Content older than 15 minutes (or than the request's wait, if that is shorter) is shown dimmed as "Updated hh:mm" whatever it last said, and never says a session needs you. The Live Activity draws only what the phone itself wrote or what the computer sealed for it: text a relay puts in a push is never shown. Nothing in them can answer a request: a tap opens the app, where the answer still needs Face ID. The Live Activity may be updated by a push the computer seals for the phone; Apple and the relay see only ciphertext.

## What it runs

- `node ~/.claude/bobix/hook.js <port>` on each Claude Code hook event, in the background so Claude never waits for it. SessionStart runs in the foreground (5 s at most, a local call) so it can name a session started from an issue; Claude lets you type meanwhile. The one exception is a permission request: there the hook waits for your answer in Bobix (Settings → "Approve from Bobix": by default until you answer there, or a time limit you set; off if you choose). Claude Code shows its own prompt in the terminal at the same time, so you can answer there instead. Runs without a person at Bobix (`claude -p`, Agent SDK apps) never wait. Answers come only from Bobix's own windows and notifications, never over the network. Fallbacks without Node.js: `curl` or PowerShell (no approvals).
- When you open a session (a pet click, **Open session** or **Open to approve** in the panel, on the pet's card or in the tray list, ↵ in ⌘K, a notification): `open -a <app>` (macOS), `WScript.Shell.AppActivate` via PowerShell (Windows) or `xdotool` (Linux) to bring the session's window forward, and `ps` / `Get-CimInstance` to find that window's process. In the Claude desktop app it opens `claude://code/continue?session=<id>`, a link that app registers; a Claude desktop session that ended while Bobix ran is opened through the same link. It is not a documented public API and may change; if it stops working, the click falls back to the session's details.
- For each folder a session works in, at most every 30 s (and on a session's start and end): `git status --porcelain=v2 --branch`, `git rev-parse --show-toplevel`, `git log -1`, `git rev-list --count HEAD --not --remotes`, `git worktree list --porcelain`, `git remote -v`. Read-only, without taking git's index lock; these reads fetch and push nothing (a Full Start fetches and **Push and open MR** pushes, only when you click: see the ticket flow below).
- Only while GitLab is on: `glab auth status` and `glab api …` as above. The same for GitHub with `gh` while GitHub is on.
- **Finding your tools** (`glab`, `gh`, `claude`, `tailscale`, `node`): an app started from the Dock or the menu does not see your shell's `PATH`, so Bobix asks your login shell, with a fixed text and only the tool's own name: `$SHELL -lc "command -v <name>"`, then `-lic` if that finds nothing (on Windows, `where <name>`). It waits 5 seconds at most per shell, and looks up each name when it is first needed. The answers for `glab`, `gh`, `node` and the `claude` of the ticket helper are looked up once per app start and again when you press Refresh; the `claude` of the habits and room drafts and `tailscale` are looked up once per app start only. The answer is only a path, kept in memory. Your shell's start-up files run as they do for any login shell.
- **Start → Quick** on an issue under Work in the panel (only when you press it): reads that issue once more through your own `glab` / `gh` (`glab api --hostname <host> projects/<project>/issues/<number>` or `gh api --hostname <host> repos/<owner>/<repo>/issues/<number>`, a GET) for its description, and shows the prompt (title, description cut at 3000 characters, link) in a box you can edit. Bobix keeps none of it. **Open session and copy prompt** copies the prompt to your clipboard and opens `claude://code/new?folder=<the project's folder>&q=<the prompt>` (the folder the Start box shows; its git remote must name a project on your signed-in hosts), Claude's [documented link](https://support.claude.com/en/articles/14729294-open-claude-desktop-with-a-link) for a new session with its prompt box filled in (the Claude app asks you to confirm the folder; nothing is sent until you press Enter there). The prompt goes only to the Claude app on this computer.
- **Skills in the Start box** (only when you press Start): Bobix lists the Claude Code skills a session in that folder can call, to suggest one. It reads only the `name`, `description` and `user-invocable` lines at the top of each `SKILL.md` in the places Claude Code keeps skills: `~/.claude/skills` (yours, and `synced/` from your claude.ai account), `.claude/skills` in the folder and its parents up to the repository root, the managed folder your organization may deploy (`/Library/Application Support/ClaudeCode` on macOS, `/etc/claude-code` on Linux, `C:\Program Files\ClaudeCode` on Windows), and the plugins in `~/.claude/plugins/installed_plugins.json` that are installed for you or for that folder and enabled (`enabledPlugins` in `~/.claude/settings.json`, the folder's `.claude/settings.json` and `.claude/settings.local.json`). Nothing is copied, kept or changed. Your role and the skills you pin (both in the **Skills** tab; your own skills are read the same way from your own skill folders and plugins) are kept in Bobix's settings. The Skills tab also lists, per project on this machine, the project's and team's skills in its folder, read the same way when you open the tab.
- **Skill process** (only when you press Start, or open the Skills screen): Bobix reads `.bobix/skills.json` at the root of the project's repository, if there is one ([format](skill-process.md)). It never writes it. A process you import in the Skills screen (per project) is read from the file you choose, or from an `https://` link when you press Import: one GET with your system's `curl`, https only, 64 KB and 10 s at most. It is kept in Bobix's settings for that project. Process files are data only. Bobix checks them strictly and runs nothing in them. For a skill the process names that Claude doesn't have, Bobix only shows a line to copy; it never installs anything, and writes to Claude's skill folders only when you click Disable or Remove in the skills audit (above). A session created afterwards where the start waits (that folder, the main folder of its repository, or a Claude worktree under it: a Full start opens in the flow's worktree, but Claude desktop may still start the session in the main folder or in a worktree it makes there) is linked to the issue once its first prompt names it (the issue's link, or `#<number> <title>`, as the prompt Bobix built does), and Bobix's UserPromptSubmit hook answers that prompt with its name (`[<code>-<number>] <short title>`, the issue's project code, as `/rename` would set it). A session you open there yourself, one already open before the start, or one after you cancel takes no name. This is the only hook output besides permission answers (and a ticket plan's approval, above); for it, the SessionStart and UserPromptSubmit hooks run in the foreground (5 s at most). Until then the issue shows "waiting for a new session" with ✕ to cancel. **Open session** (for a running session) does what a click on its pet does; **Resume**, for a session Bobix doesn't see running, opens `claude://code/continue?session=<id>` for the newest Claude desktop session in that folder with the issue's name.
- **Ticket flow** (Work, only when you press it): **Prepare start** runs `git remote` and `git ls-remote --heads <the remote>` to list the branches you can start from (`origin`, else the first remote; with your own git credentials; offline or refused, Start stops and says so). **Start in Claude** reads the issue's description as Start does (above), runs `git ls-remote` again (the picked branch must still be there), `git fetch --quiet <the remote> +refs/heads/<the branch>:refs/remotes/<the remote>/<the branch>` (30 s at most, so the branch you picked is the latest one and never a local copy), `git rev-parse` (the worktree must be on that commit, or it is removed again), `git worktree move` (only a worktree Bobix made in the old place, `.claude/worktrees/bobix-<number>`, still on the ticket's branch), `git worktree remove --force` on a worktree of the ticket's branch whose folder is gone (git only forgets it) and `git worktree add` in the project's repository (above), copies the prompt and opens `claude://code/new?folder=<the worktree>&q=<the prompt>`; **Copy terminal command** copies `cd <the worktree> && claude --model <model> --permission-mode plan '<the prompt>'` for you to paste (the desktop link can't preset a model or plan mode). The prompt names the ticket's worktree and branch and says what to do when Claude opened the session somewhere else (stay in a worktree Claude made for it; from the repository's main folder, `cd` into the ticket's worktree first and leave files that were already changed alone). When the session that took the start runs outside the ticket's worktree, Bobix reads `git status` there once (in the main folder: how many files of yours were not committed, without the worktrees under `.claude/worktrees`; in a worktree Claude made: how many commits there no remote has, `git rev-list --count HEAD --not --remotes`, since Claude cuts it from your main folder) and shows it under Work and in Open MR. It asks the session to restate the ticket and wait for your confirmation, to ask what the code cannot answer through `AskUserQuestion` (each question with its source, a tag and an "Out of scope for this ticket" choice), then to plan with a requirement → step mapping and its assumptions, names the four cases it must stop for (pushing to the main branch, deleting data, calling hosts the project does not already use, touching secrets), the work log's template, and two steps before done: run the project's tests, build and lint and paste each command with its last lines of output under `## Checks` (or say there are none), then review the change against the plan and the assumptions with `/code-review` and note it there. A flow marked done without checks shows a warning; Bobix does not block it. **Review in Claude** on a done flow opens `claude://code/new?folder=<the worktree>&q=<a review prompt>` (a second session that reviews the branch against its plan, changes no code and adds a line under `## Checks`); **Copy review command** copies the same as `cd <the worktree> && claude --model <the split's review model, else opus> --permission-mode auto '<the prompt>'` for you to paste. When the session asks you a question (Claude's `AskUserQuestion`), the pet shows it waiting with the question's text; Bobix does not hold or answer it (you answer in Claude). That session's plan (Claude's `ExitPlanMode` request, which hook.js now forwards with the plan, up to 20 000 characters) is held until you answer it, whatever the pets show. **Approve plan** answers it with `allow`, the plan given back as Claude requires, and `setMode: auto` for that session only, as Claude's own "Yes, and use auto mode" does; **Ask for changes** answers `deny` with your text. Bobix writes no permission rules and no Claude settings: the four stops are Claude's own auto mode. Haiku runs as `claude -p --model haiku --tools "" --no-session-persistence --strict-mcp-config --settings {"disableAllHooks":true} --output-format json`: no tools, no MCP server, no hook (no pet for it) and no saved session. **Open MR…** on a done flow shows the merge request's title and description, made from the work log (the issue it closes, the plan, the assumptions, the checks); you can edit them, and nothing is sent until you press **Push and open MR**. That counts the commits on the ticket's branch (`git rev-list --count <start>..<branch>`; with none, nothing is pushed and Bobix says so), then runs `git push -u origin <the ticket's branch>` in the worktree, or in the repository's main folder when the worktree was deleted by hand (with your own git credentials; never the default branch; in a worktree Claude made, the branch that folder is on) and then your own `glab mr create --repo https://<host>/<project> --source-branch <branch> --target-branch <the branch the ticket started from> --title … --description … --yes`. On a GitHub issue the button is **Push and open pull request**: the same push, then your own `gh pr create --repo <owner>/<repo> --head <branch> --base <the branch the ticket started from> --title … --body …` (with `GH_HOST` set to the issue's host). Only that title and description go to GitLab or GitHub; the work log stays on this computer. Bobix keeps the MR's or pull request's link with the flow. **Clean up worktree** first counts the branch's commits that no remote has (`git rev-list --count <branch> --not --remotes`) and says so; a second click cleans up anyway (the branch stays). After that, while GitLab is on, Bobix reads that merge request's head pipeline with your own `glab api --hostname <host> projects/<project>/merge_requests/<n>` (a GET) at each issue read and when you press **Check CI**, until it is merged or closed: it keeps the pipeline's status and link. For a pull request, while GitHub is on, the same reads are `gh pr view <n> --repo <owner>/<repo> --json state` and `gh pr checks <n> --repo <owner>/<repo> --json bucket,link,name` (both read-only): it keeps the checks' overall status and one link (the first failed check's, else the first check's). **Copy Fix CI** copies a prompt for the ticket's session; nothing is sent.
- **Code in another repository** (the Start box's **Fix it in which project?**, only what you pick): an issue can live in one repository while its code is in another. The worktree, the session, the MR / PR and its CI then go in the repository you picked, and the MR / PR's description closes the issue across repositories (`Closes group/issue-repo#123`, `Closes owner/repo#123` on GitHub). Bobix keeps your pick per issue repository in its settings (`workCode`) as the next Start's suggestion. **Start in another project…** on a ticket starts the same issue again in a second repository: its own worktree, session and MR / PR, all shown on the issue. The repositories offered are the ones the repo picker read (above); nothing more is read for it.
- **Where a repository's code is** (Start on an issue whose repository Bobix knows no folder of yet, under Work, only when you press it). Bobix asks once per repository and remembers the answer (Settings → Work → Project folders, each with Forget). **Change folder…** next to the folder in the Start box does the same for a project Bobix already knows: the folder you pick, once its remote checks out, replaces the remembered one, and a folder you chose or cloned wins over the folder a session runs in. **Choose folder…** opens a folder dialog, then runs `git status` and `git remote -v` there (as for a session's folder) and remembers the folder only when one of its remotes names that project (https and ssh forms alike, every remote, a fork's upstream too, and a host written as an `~/.ssh/config` alias counts for its real host: see below); otherwise it says which project the folder is, or that it is not a git repository. **Clone…** opens a folder dialog for where to put it, then runs your own `glab repo clone https://<host>/<project> <folder>/<name>` (GitLab) or `gh repo clone <owner>/<repo> <folder>/<name>` (GitHub), with your own sign-in, and remembers the clone once its remote checks out. Nothing is cloned without that click. The Start box has the same **Clone…** next to **Change folder…**, for a fresh copy of a project Bobix already knows. A clone never goes into a folder that is there, does not start with under 1 GB free there, and one that fails is removed (the folder it began; nothing else is touched, and nothing is remembered).
- **Habits become skills**: `claude -p --model haiku|sonnet --output-format text --no-session-persistence --strict-mcp-config --settings {"disableAllHooks":true} --tools <none, or Skill,Read for a draft>`, the prompt on its standard input, in the app's settings folder → `habit-skills/work`, found the way your shell finds `claude` (a login shell's `command -v claude`). No session is saved, no hook (Bobix's own included) and no MCP server runs, and Claude's settings files are not written. A scan gives up after 3 minutes, a draft after 7.
- **War room**: `tailscale ip -4` and `tailscale whois --json <address>` (read-only, Tailscale's own CLI), found the way your shell finds `tailscale`, else `/usr/local/bin/tailscale` or inside the Tailscale app. Bobix never changes Tailscale's settings. The draft runs `claude -p --model sonnet --output-format text --no-session-persistence --strict-mcp-config --settings {"disableAllHooks":true} --tools ""` with the room's chat on its standard input, in the app's settings folder → `rooms/work`.
- Arguments are passed as lists, never built into a command line for a shell. Exceptions, all with fixed text: the login-shell lookup above; on Windows, PowerShell runs a fixed script to read the process list and to bring a session's window forward (`Get-CimInstance`, `WScript.Shell.AppActivate`, above); and the commands Bobix only **copies** to your clipboard for you to paste into your own shell, **Copy terminal command** and **Copy review command** under Work: `cd '<the worktree>' && claude --model '<model>' --permission-mode <plan|auto> '<the prompt>'`. The prompt there is the ticket's start prompt (the issue's title, description cut at 3000 characters, and link) or, for the review command, a review prompt, with single quotes escaped; Bobix never runs that text, and it stays on your clipboard until something else replaces it. **Copy command** on an ended terminal session copies `claude --resume <id>` the same way (the id has letters, digits, `-` and `_` only).

## Your organization's policies

Bobix only uses Claude Code's documented hooks. If your organization's managed settings allow only managed hooks (`allowManagedHooksOnly`), Claude Code does not run Bobix's hooks and the app receives nothing. Bobix does not try to work around that.
