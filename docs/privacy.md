# Privacy and security

Bobix runs on your computer. It has no account and no analytics, and nothing goes to Bobix's author. By default it makes two kinds of request: once a day it reads GitHub's update list to see whether a newer version exists (you can turn that off; it downloads a new version only when you press Update), and the panel reads the open issues of the GitLab and GitHub repositories you pick, through your own `glab` and `gh`, wherever you signed them in (on by default; one switch each turns it off, below). Text goes to Anthropic only for the features you switch on or press (the weekly habits scan, the ticket helper, the war room draft: below), through your own `claude -p` and your own Claude sign-in, as any prompt you send Claude does. While you host a war room, the people you invite reach that room over your Tailscale network (below).

> **What is built.** Everything below is how Bobix works today, including the parts that arrived in the 0.2 test builds: usage per session, the skills audit and model rules, the ticket flow under Work, habits into skills and the war room. Each one asks before it does anything that reaches beyond reading: reading what you write in sessions is off by default (counts only); the skills audit may move your skills and edit a project's `CLAUDE.md` only when you click, with a backup and an undo; habits into skills asks Haiku through your own `claude -p` once a week, only with two switches on, and writes to `~/.claude/skills` only when you approve; the war room opens a second port, on your Tailscale address only, while you host a room. The [product direction](product-direction.md) records why.

The hook script drops file contents and tool output before sending anything. All of this is kept **in memory only** and forgotten when a session ends or the app quits, except a finished session's usage numbers (`usage.json`, below).

Usage never uses your Claude login: Bobix reads no credential, calls no account or quota API and writes nothing to Claude's files. The real 5-hour and weekly limits of a subscription are only in Claude's own `/usage`; the dollar figure is an estimate at public API prices (a switch in Settings hides it).

## What it sends, and to whom

- **Nothing goes to Bobix's author or to any server of Bobix.** What leaves your computer goes only where this section says: GitHub's update list and, when you press Update, the update file, the issue reads through your own `glab` / `gh`, feedback you submit yourself, and the `claude -p` calls of the features you switch on or press, which go to Anthropic under your own Claude sign-in (the weekly habits scan and draft, the ticket helper, the war room draft). Only when you click, Bobix also runs your own `git` and `glab` / `gh` against your own remotes: a Full Start fetches the project's remote (`git fetch`), **Push and open MR / pull request** pushes the ticket's branch and creates it, and a skill process imported from an `https://` link is one GET with your system's `curl`. Each is described below. Fonts and images are bundled.
- **New version check** (Settings → "Tell me about new versions", on by default; Settings → App → Updates → **Check now** does the same when you press it, even with the switch off): once a day the app reads one small JSON file from GitHub: `https://github.com/baonguyen-agilityio/bobix/releases/latest/download/latest.json`, the update list of the latest stable release, or, only while Settings → **Get test builds** is on (off by default), `https://github.com/baonguyen-agilityio/bobix/releases/download/test-channel/test.json`. GitHub redirects the request to its file host. The request carries no data about you or your sessions: GitHub sees what any web page sees (your IP address) and the program name `tauri-plugin-updater/<its version>`. No account or token is used. The list names the newest version and where its files are.
- **Updating** (only when you press **Update**, in Settings, the tray menu or a notification): the app downloads the update file for your system from the same release on `github.com` (the same file as the installer on Windows and Linux), checks its signature against the public key built into the app, and only then installs it. A file that fails the check is never installed. Nothing is sent but the download request itself. On Linux the package manager asks for your password; on macOS an app installed where only an administrator can write asks for it too. Before the restart Bobix tells you about held permission requests and running ticket flows, and the held requests go back to Claude's own prompt.
- **Feedback** (Settings → Feedback in the panel, or the tray menu, only when you use it): opens GitHub's new-issue form in your browser with your text filled in. Nothing is sent until you submit it there, with your GitHub account, and the issue is public. A bug report also fills in technical details: the app version, operating system, hook state, some settings, session states and recent errors with folders and tokens removed. You can read them before opening the form. No prompts, code, project names or tokens. An idea carries no technical details.
- **GitLab issues** (Settings → Work (GitLab, GitHub): "GitLab issues", **on by default**; it reads only where your own glab is signed in): Bobix runs your own `glab auth status` to learn which GitLab hosts you are signed in to, and as whom (it reads only the "Logged in to <host> as <name>" lines; glab masks the token there; the name tells which issues are assigned to you). The first time a host is read, `glab api --hostname <host> projects?membership=true&simple=true&order_by=last_activity_at&per_page=100` (up to 5 pages) lists the projects you are a member of, and the ones active in the last 90 days are ticked. The ticks are kept in Bobix's settings (`workRepos`); you change them in Work → Repos to list, which reads that list again when you open it (and on **Read again**). Then, when the app starts, every 5 minutes, when you press Refresh and when you change the filter or the page: for each ticked project, `projects/<project>/issues?state=opened&order_by=updated_at&sort=desc&per_page=<n>&page=<p>` (with `scope=assigned_to_me` for **Mine**, `assignee_id=None` for **Unassigned**), one read (GET) per project, as many issues as the page shown needs plus one. With more than 20 projects ticked, Work warns and suggests unticking some. With it, two more reads per host: `merge_requests?scope=created_by_me&state=opened&per_page=100` (your open merge requests: an issue one of them closes, by "Closes #n" in its description or a branch named `<n>-…`, waits for review) and `issues?scope=assigned_to_me&state=closed&updated_after=<4 days ago>&per_page=100` (the board keeps those closed today, for "Done today" and the report, and those closed on the last working day, for the stand-up). When a session here works on an issue that is not in the list (its branch `<n>-…` or its start names it), Bobix reads that one issue too (`projects/<project>/issues/<n>`, a GET, once per issue, at most 10 per read) so the session shows under its ticket; it drops it once no session works on it or it is closed. Bobix writes to GitLab only when you press **Push and open MR** on a ticket (below). `glab` uses the sign-in you made yourself (`glab auth login --hostname <host>`); Bobix never signs in for you, never reads or stores the token, and sends nothing about your prompts, sessions or code, only those requests. It keeps the issues' number, title, project, labels, due date, assignees' names, last update and link in memory, and the list of projects for the picker. Off, Bobix makes no GitLab request at all. Links open in your browser, and only links of the issues it read.
- **GitHub issues** (Settings → Work (GitLab, GitHub): "GitHub issues", **on by default**; it reads only where your own gh is signed in): the same, through your own `gh`. Bobix runs `gh auth status` to learn which GitHub hosts (github.com, GitHub Enterprise) you are signed in to; it reads only the "Logged in to <host> account <name>" lines and the "Active account" line after each (gh masks the token there), so with several accounts on one host it uses the active one, as `gh` itself does, and that name tells which issues are yours. The first time a host is read, `gh api --hostname <host> user/repos?per_page=100&sort=pushed` (up to 5 pages: the repositories you own, collaborate on or reach through an organization) gives the picker's list and the first ticks (active in the last 90 days). The issues of the ticked repositories, at the same times as GitLab's: `gh api --hostname <host> -X GET search/issues -f q="is:issue is:open repo:<owner>/<repo> …" -f sort=updated -f order=desc -f per_page=<n> -f page=<p>` (with `assignee:@me` for **Mine**, `no:assignee` for **Unassigned**), one search (GET) per 30 ticked repositories. With it, `gh api --hostname <host> graphql` with a query (no mutation) for your open pull requests and the issues each one closes, `issues?filter=assigned&state=closed&since=<4 days ago>&per_page=100` for the issues closed today and on the last working day, and `repos/<owner>/<repo>/issues/<n>` for an issue a session here works on that is not in the list (as for GitLab above). It keeps a pull request's link and the issue numbers it closes. Bobix writes to GitHub only when you press **Push and open pull request** on a ticket (below). It never signs in for you (`gh auth login`), never reads or stores the token, and keeps the same fields in memory (no due date: GitHub issues have none). Off, Bobix makes no request through gh at all.
- Both switches used to be off by default. Settings from a Bobix before the repo picker turn both on once, as on a new install; each still reads only where its CLI is signed in, and a switch you turn off after that stays off.
- **Habits become skills** (only while Settings → Usage → "Read my prompts to count them by kind" and "the weekly scan" are both on; both are off by default): once a week, and when you press Scan now, Bobix runs your own `claude -p` with Haiku and gives it the prompts you typed in the last 14 days (the newest 300, each cut at 400 characters), so they go to Anthropic under your own Claude sign-in, as any prompt you send Claude does. When you press Draft, it runs `claude -p` with Sonnet and gives it the kind of request, up to three prompts from each of the kind's best sessions, and, for an improvement, the skill file as it is (your own `~/.claude/skills/<name>/SKILL.md`, or an existing similar skill's when a new one is drafted) and the prompts you typed after using it. A draft lets Claude use its `Skill` and `Read` tools: the prompt asks only for the skill, but Claude may read files on this computer, and what it reads goes to Anthropic in that conversation. Bobix never reads your Claude credentials; `claude` uses its own sign-in.
- **War room** (the Room tab, only when you create or join a room). Hosting: while you host a room that is not decided yet, Bobix listens on a second port (4748), bound to this computer's Tailscale address only (`tailscale ip -4`), never on all interfaces. The panel's own server stays on `127.0.0.1` with its token. A request is answered only if it comes from a Tailscale address, carries Bobix's room header with this address as its Host (so a web page can't reach it), and its sender's login (`tailscale whois`) is one you invited to that room; anyone else gets a refusal, which the audit log records. What crosses that port: the room as you and your guests typed it (title, problem, the chat messages with who sent them and when, the draft of the record, the decision, the invited logins and the people's names and device names). Each guest writes the decision record itself from that, never from HTML the host sends. What never does: transcripts, logs, session data or anything else from this computer. Joining: Bobix sends the host only the messages you type or paste into the room (`{ text }`). Before anything is sent, and again when the host stores it, common secret shapes (private keys, GitHub / GitLab / Slack / OpenAI / Anthropic / AWS / Google tokens, JWTs, `Bearer …`, passwords in URLs, `password=` / `token:` and similar) are replaced by `[redacted]`; this catches common shapes, not every possible secret, so don't paste one. The draft: when the host presses Draft, only the host's own `claude -p` (Sonnet), on the host's computer, reads the chat once and arranges it into problem, options, pros and cons (no session saved, no hooks, no MCP servers, no tools). The chat goes to Anthropic under the host's own Claude sign-in, as any prompt does; guests' Claude accounts never see it. The host edits that draft and decides. **Copy for Claude** (host only, after a warning) copies the record's text so you can paste it into claude.ai yourself: Claude's command line has no way to publish an artifact. The first time you host a room, macOS may ask once whether Bobix may accept incoming connections (builds that are not signed are not allowed on their own): allow it, or invited people can't reach the room; the Room tab says so too.
- Hooks talk to the app over `127.0.0.1` only. The server checks the Host header (blocks DNS rebinding) and requires the per-user token on every event and on the state stream, so web pages and other users on the same machine can neither feed it nor read it.
- **Ticket flow, Haiku** (Work, only when you click **Ask Haiku to propose** or **Fill gaps with Haiku**): Bobix runs your own `claude -p` with Haiku, with the issue's title and description (cut at 3000 characters) to propose a split and models, or with the work log, the branch's commit subjects and its changed-file list to sum up what the log leaves out. They go to Anthropic under your own Claude sign-in, as any prompt you send Claude does. Nothing else is sent; the work log itself is never shared.
- **Notifications** show a session's request or the start of its final answer through your operating system. They can appear while you share your screen; turn them off or use **Pause notifications** in Settings.

## What it runs

- `node ~/.claude/bobix/hook.js <port>` on each Claude Code hook event, in the background so Claude never waits for it. SessionStart runs in the foreground (5 s at most, a local call) so it can name a session started from an issue; Claude lets you type meanwhile. The one exception is a permission request: there the hook waits for your answer in Bobix (Settings → "Approve from Bobix": by default until you answer there, or a time limit you set; off if you choose). Claude Code shows its own prompt in the terminal at the same time, so you can answer there instead. Runs without a person at Bobix (`claude -p`, Agent SDK apps) never wait. Answers come only from Bobix's own windows and notifications, never over the network. Fallbacks without Node.js: `curl` or PowerShell (no approvals).
- When you click a pet: `open -a <app>` (macOS), `WScript.Shell.AppActivate` via PowerShell (Windows) or `xdotool` (Linux) to bring the session's window forward, and `ps` / `Get-CimInstance` to find that window's process. In the Claude desktop app it opens `claude://code/continue?session=<id>`, a link that app registers. It is not a documented public API and may change; if it stops working, the click falls back to the session's details.
- For each folder a session works in, at most every 30 s (and on a session's start and end): `git status --porcelain=v2 --branch`, `git rev-parse --show-toplevel`, `git log -1`, `git rev-list --count HEAD --not --remotes`, `git worktree list --porcelain`, `git remote -v`. Read-only, without taking git's index lock; these reads fetch and push nothing (a Full Start fetches and **Push and open MR** pushes, only when you click: see the ticket flow below).
- Only while GitLab is on: `glab auth status` and `glab api …` as above. The same for GitHub with `gh` while GitHub is on.
- **Finding your tools** (`glab`, `gh`, `claude`, `tailscale`, `node`): an app started from the Dock or the menu does not see your shell's `PATH`, so Bobix asks your login shell, with a fixed text and only the tool's own name: `$SHELL -lc "command -v <name>"`, then `-lic` if that finds nothing (on Windows, `where <name>`). It waits 5 seconds at most per shell, and looks up each name when it is first needed. The answers for `glab`, `gh`, `node` and the `claude` of the ticket helper are looked up once per app start and again when you press Refresh; the `claude` of the habits and room drafts and `tailscale` are looked up once per app start only. The answer is only a path, kept in memory. Your shell's start-up files run as they do for any login shell.
- **Start → Quick** on an issue under Work in the panel (only when you press it): reads that issue once more through your own `glab` / `gh` (`glab api --hostname <host> projects/<project>/issues/<number>` or `gh api --hostname <host> repos/<owner>/<repo>/issues/<number>`, a GET) for its description, and shows the prompt (title, description cut at 3000 characters, link) in a box you can edit. Bobix keeps none of it. **Open session and copy prompt** copies the prompt to your clipboard and opens `claude://code/new?folder=<the project's folder>&q=<the prompt>` (the folder the Start box shows; its git remote must name a project on your signed-in hosts), Claude's [documented link](https://support.claude.com/en/articles/14729294-open-claude-desktop-with-a-link) for a new session with its prompt box filled in (the Claude app asks you to confirm the folder; nothing is sent until you press Enter there). The prompt goes only to the Claude app on this computer.
- **Skills in the Start box** (only when you press Start): Bobix lists the Claude Code skills a session in that folder can call, to suggest one. It reads only the `name`, `description` and `user-invocable` lines at the top of each `SKILL.md` in the places Claude Code keeps skills: `~/.claude/skills` (yours, and `synced/` from your claude.ai account), `.claude/skills` in the folder and its parents up to the repository root, the managed folder your organization may deploy (`/Library/Application Support/ClaudeCode` on macOS, `/etc/claude-code` on Linux, `C:\Program Files\ClaudeCode` on Windows), and the plugins in `~/.claude/plugins/installed_plugins.json` that are installed for you or for that folder and enabled (`enabledPlugins` in `~/.claude/settings.json`, the folder's `.claude/settings.json` and `.claude/settings.local.json`). Nothing is copied, kept or changed. Your role and the skills you pin (both in the **Skills** tab; your own skills are read the same way from your own skill folders and plugins) are kept in Bobix's settings. The Skills tab also lists, per project on this machine, the project's and team's skills in its folder, read the same way when you open the tab.
- **Skill process** (only when you press Start, or open the Skills screen): Bobix reads `.bobix/skills.json` at the root of the project's repository, if there is one ([format](skill-process.md)). It never writes it. A process you import in the Skills screen (per project) is read from the file you choose, or from an `https://` link when you press Import: one GET with your system's `curl`, https only, 64 KB and 10 s at most. It is kept in Bobix's settings for that project. Process files are data only. Bobix checks them strictly and runs nothing in them. For a skill the process names that Claude doesn't have, Bobix only shows a line to copy; it never installs anything, and writes to Claude's skill folders only when you click Disable or Remove in the skills audit (above). A session created afterwards where the start waits (that folder, the main folder of its repository, or a Claude worktree under it: a Full start opens in the flow's worktree, but Claude desktop may still start the session in the main folder or in a worktree it makes there) is linked to the issue once its first prompt names it (the issue's link, or `#<number> <title>`, as the prompt Bobix built does), and Bobix's UserPromptSubmit hook answers that prompt with its name (`[<code>-<number>] <short title>`, the issue's project code, as `/rename` would set it). A session you open there yourself, one already open before the start, or one after you cancel takes no name. This is the only hook output besides permission answers (and a ticket plan's approval, above); for it, the SessionStart and UserPromptSubmit hooks run in the foreground (5 s at most). Until then the issue shows "waiting for a new session" with ✕ to cancel. **Resume** does what a click on the session's pet does, or, for a session Bobix doesn't see running, opens `claude://code/continue?session=<id>` for the newest Claude desktop session in that folder with the issue's name.
- **Ticket flow** (Work, only when you press it): **Start in Claude** reads the issue's description as Start does (above), runs `git rev-parse`, `git fetch --quiet <the remote>` (30 s at most; `origin`, else the first remote; with your own git credentials, so the latest default branch is the start point) and, when the remote's `HEAD` is not known yet, `git remote set-head <the remote> --auto`, `git worktree move` (only a worktree Bobix made in the old place, `.claude/worktrees/bobix-<number>`, still on the ticket's branch), `git worktree remove --force` on a worktree of the ticket's branch whose folder is gone (git only forgets it) and `git worktree add` in the project's repository (above), copies the prompt and opens `claude://code/new?folder=<the worktree>&q=<the prompt>`; **Copy terminal command** copies `cd <the worktree> && claude --model <model> --permission-mode plan '<the prompt>'` for you to paste (the desktop link can't preset a model or plan mode). The prompt names the ticket's worktree and branch and says what to do when Claude opened the session somewhere else (stay in a worktree Claude made for it; from the repository's main folder, `cd` into the ticket's worktree first and leave files that were already changed alone). When the session that took the start runs outside the ticket's worktree, Bobix reads `git status` there once (in the main folder: how many files of yours were not committed, without the worktrees under `.claude/worktrees`; in a worktree Claude made: how many commits there no remote has, `git rev-list --count HEAD --not --remotes`, since Claude cuts it from your main folder) and shows it under Work and in Open MR. It asks the session to restate the ticket and wait for your confirmation, to ask what the code cannot answer through `AskUserQuestion` (each question with its source, a tag and an "Out of scope for this ticket" choice), then to plan with a requirement → step mapping and its assumptions, names the four cases it must stop for (pushing to the main branch, deleting data, calling hosts the project does not already use, touching secrets), the work log's template, and two steps before done: run the project's tests, build and lint and paste each command with its last lines of output under `## Checks` (or say there are none), then review the change against the plan and the assumptions with `/code-review` and note it there. A flow marked done without checks shows a warning; Bobix does not block it. **Review in Claude** on a done flow opens `claude://code/new?folder=<the worktree>&q=<a review prompt>` (a second session that reviews the branch against its plan, changes no code and adds a line under `## Checks`); **Copy review command** copies the same as `cd <the worktree> && claude --model <the split's review model, else opus> --permission-mode auto '<the prompt>'` for you to paste. That session's plan (Claude's `ExitPlanMode` request, which hook.js now forwards with the plan, up to 20 000 characters) is held until you answer it, whatever the pets show. **Approve plan** answers it with `allow`, the plan given back as Claude requires, and `setMode: auto` for that session only, as Claude's own "Yes, and use auto mode" does; **Ask for changes** answers `deny` with your text. Bobix writes no permission rules and no Claude settings: the four stops are Claude's own auto mode. Haiku runs as `claude -p --model haiku --tools "" --no-session-persistence --strict-mcp-config --settings {"disableAllHooks":true} --output-format json`: no tools, no MCP server, no hook (no pet for it) and no saved session. **Open MR…** on a done flow shows the merge request's title and description, made from the work log (the issue it closes, the plan, the assumptions, the checks); you can edit them, and nothing is sent until you press **Push and open MR**. That counts the commits on the ticket's branch (`git rev-list --count <start>..<branch>`; with none, nothing is pushed and Bobix says so), then runs `git push -u origin <the ticket's branch>` in the worktree, or in the repository's main folder when the worktree was deleted by hand (with your own git credentials; never the default branch; in a worktree Claude made, the branch that folder is on) and then your own `glab mr create --repo https://<host>/<project> --source-branch <branch> --title … --description … --yes`. On a GitHub issue the button is **Push and open pull request**: the same push, then your own `gh pr create --repo <owner>/<repo> --head <branch> --title … --body …` (with `GH_HOST` set to the issue's host). Only that title and description go to GitLab or GitHub; the work log stays on this computer. Bobix keeps the MR's or pull request's link with the flow. **Clean up worktree** first counts the branch's commits that no remote has (`git rev-list --count <branch> --not --remotes`) and says so; a second click cleans up anyway (the branch stays). After that, while GitLab is on, Bobix reads that merge request's head pipeline with your own `glab api --hostname <host> projects/<project>/merge_requests/<n>` (a GET) at each issue read and when you press **Check CI**, until it is merged or closed: it keeps the pipeline's status and link. For a pull request, while GitHub is on, the same reads are `gh pr view <n> --repo <owner>/<repo> --json state` and `gh pr checks <n> --repo <owner>/<repo> --json bucket,link,name` (both read-only): it keeps the checks' overall status and one link (the first failed check's, else the first check's). **Copy Fix CI** copies a prompt for the ticket's session; nothing is sent.
- **Code in another repository** (the Start box's **Fix it in which project?**, only what you pick): an issue can live in one repository while its code is in another. The worktree, the session, the MR / PR and its CI then go in the repository you picked, and the MR / PR's description closes the issue across repositories (`Closes group/issue-repo#123`, `Closes owner/repo#123` on GitHub). Bobix keeps your pick per issue repository in its settings (`workCode`) as the next Start's suggestion. **Start in another project…** on a ticket starts the same issue again in a second repository: its own worktree, session and MR / PR, all shown on the issue. The repositories offered are the ones the repo picker read (above); nothing more is read for it.
- **Where a repository's code is** (Start on an issue whose repository Bobix knows no folder of yet, under Work, only when you press it). Bobix asks once per repository and remembers the answer (Settings → Work → Project folders, each with Forget). **Change folder…** next to the folder in the Start box does the same for a project Bobix already knows: the folder you pick, once its remote checks out, replaces the remembered one, and a folder you chose or cloned wins over the folder a session runs in. **Choose folder…** opens a folder dialog, then runs `git status` and `git remote -v` there (as for a session's folder) and remembers the folder only when one of its remotes names that project (https and ssh forms alike, every remote, a fork's upstream too, and a host written as an `~/.ssh/config` alias counts for its real host: see below); otherwise it says which project the folder is, or that it is not a git repository. **Clone…** opens a folder dialog for where to put it, then runs your own `glab repo clone https://<host>/<project> <folder>/<name>` (GitLab) or `gh repo clone <owner>/<repo> <folder>/<name>` (GitHub), with your own sign-in, and remembers the clone once its remote checks out. Nothing is cloned without that click. The Start box has the same **Clone…** next to **Change folder…**, for a fresh copy of a project Bobix already knows. A clone never goes into a folder that is there, does not start with under 1 GB free there, and one that fails is removed (the folder it began; nothing else is touched, and nothing is remembered).
- **Habits become skills**: `claude -p --model haiku|sonnet --output-format text --no-session-persistence --strict-mcp-config --settings {"disableAllHooks":true} --tools <none, or Skill,Read for a draft>`, the prompt on its standard input, in the app's settings folder → `habit-skills/work`, found the way your shell finds `claude` (a login shell's `command -v claude`). No session is saved, no hook (Bobix's own included) and no MCP server runs, and Claude's settings files are not written. A scan gives up after 3 minutes, a draft after 7.
- **War room**: `tailscale ip -4` and `tailscale whois --json <address>` (read-only, Tailscale's own CLI), found the way your shell finds `tailscale`, else `/usr/local/bin/tailscale` or inside the Tailscale app. Bobix never changes Tailscale's settings. The draft runs `claude -p --model sonnet --output-format text --no-session-persistence --strict-mcp-config --settings {"disableAllHooks":true} --tools ""` with the room's chat on its standard input, in the app's settings folder → `rooms/work`.
- Arguments are passed as lists, never built into a command line for a shell. Exceptions, all with fixed text: the login-shell lookup above; on Windows, PowerShell runs a fixed script to read the process list and to bring a session's window forward (`Get-CimInstance`, `WScript.Shell.AppActivate`, above); and the two commands Bobix only **copies** to your clipboard for you to paste into your own shell, **Copy terminal command** and **Copy review command** under Work: `cd '<the worktree>' && claude --model '<model>' --permission-mode <plan|auto> '<the prompt>'`. The prompt there is the ticket's start prompt (the issue's title, description cut at 3000 characters, and link) or, for the review command, a review prompt, with single quotes escaped; Bobix never runs that text, and it stays on your clipboard until something else replaces it.

## Your organization's policies

Bobix only uses Claude Code's documented hooks. If your organization's managed settings allow only managed hooks (`allowManagedHooksOnly`), Claude Code does not run Bobix's hooks and the app receives nothing. Bobix does not try to work around that.
