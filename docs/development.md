# Developing Bobix

What is missing, unreleased or unverified: [roadmap.md](roadmap.md).

For contributors. To **use** Bobix, install it from the [latest release](https://github.com/baonguyen-agilityio/bobix/releases/latest) as the [README](../README.md#install) shows; don't build it from source for that.

## Run and test

Requires Node.js 22+ and Rust (stable, via [rustup](https://rustup.rs)). On Linux also the WebKitGTK and tray libraries:
`sudo apt install libwebkit2gtk-4.1-dev librsvg2-dev libayatana-appindicator3-dev`.

```bash
git clone https://github.com/baonguyen-agilityio/bobix.git && cd bobix
npm install
npm run tauri dev    # run the app from source
npm test             # node tests (pages, pixel art, hook.js); not test/overlay.test.js, which needs Chrome
cd src-tauri && cargo test   # Rust tests (add `--features phones` for phone access, which is off by default) (state, settings, hooks, server, Work tab, picture store...)
```

A copy run from source and an installed Bobix share the same port, settings and hooks. To run one next to the installed
app, give it its own: `BOBIX_PORT=4767 BOBIX_DATA_DIR=/tmp/bobix-data BOBIX_HOME=/tmp/bobix-home npm run tauri dev`
(`BOBIX_HOME` keeps hooks and start-at-login files out of your real home).

## Process

How a change gets made, by people and by Claude Code sessions alike. The working rules a session follows are in [`CLAUDE.md`](../CLAUDE.md).

1. **Issue.** Every task starts as a GitHub issue: the problem, what done looks like, and its edge cases (each one is checked before the merge).
2. **Prototype, when needed.** A new screen, a large layout change or a new area is first drawn as a prototype in a file **outside the repository**, with made-up data, and the owner approves it before the issue is written. Fixes and small changes need none. Prototypes, mockups and videos are never committed or put in a pull request.
3. **Worktree.** One git worktree per task, cut from `origin/develop` (`git fetch origin && git worktree add .claude/worktrees/<n>-<slug> -b <type>/<n>-<slug> origin/develop`). The main checkout stays on a clean `develop`. `.claude/worktrees/` is ignored by git. Remove the worktree and its test copies when the task ends.
4. **Pull request** to `develop` with "Closes #N". The [template](../.github/pull_request_template.md) is the definition of done: edge cases verified, tests with their output, tried in the real app with made-up data, EN and VI, docs and roadmap, CI green, every review comment answered.
5. **Review.** [`claude-review.yml`](../.github/workflows/claude-review.yml) runs two steps on every pull request from a branch of this repository, both on Opus at high effort, and comments on it: the code-review plugin, and a **docs check** that says where the README, the site, `docs/` (privacy, roadmap, install, development, work model), `CLAUDE.md` or an app string (EN and VI) no longer matches what the pull request changes. The docs check names the stale file and line in the comment, stays silent on a change nobody can see (a test, CI), and does not repeat a comment already on the pull request after a new push. Neither step approves, merges or blocks. Each comment is answered, one by one: fixed, or not an issue with the reason. It needs the repository secret `CLAUDE_CODE_OAUTH_TOKEN` (made by the owner with `claude setup-token`) and the Claude GitHub App; without the secret the job ends green with a notice, and it skips fork and bot (Dependabot) pull requests. Nothing but the owner handles the token.

   **The workflow file must be identical on `main` and `develop`.** The action refuses to run unless the file on the pull request's branch equals the one on `main`, so a pull request that edits it is always skipped; the job then ends green but shows a warning ("Claude review skipped") and a note in its summary, so a skipped review is not mistaken for a passed one. Land a change to this file as two pull requests with the same file: one to `develop`, one to `main`. The docs check is a prompt inside the workflow, not a skill file, so that one file is all `main` needs. One run per pull request at a time; each step has its own turn limit (25) and time limit (15 minutes), the job 30.
6. **CI.** The three smoke checks (see [CI](#ci)) must pass.
7. **The owner approves the merge.** Sessions never merge, and never `gh pr merge --auto`. A new feature is tried by hand by the owner first.

[`dependabot.yml`](../.github/dependabot.yml) opens one weekly pull request per ecosystem and directory (cargo for `src-tauri`, `crates/bobix-link` and its `fuzz` crate, and `relay`; npm; GitHub Actions). The smoke checks run on it; the review skips it. Read it like any other pull request before the owner merges it.

## Build installers

```bash
npm run tauri build   # installers land in src-tauri's build folder, under bundle/
```

Installers have fixed names (`Bobix-mac-arm64.dmg`, `Bobix-mac-x64.dmg`, `Bobix-windows-x64.exe`, `bobix-linux-amd64.deb`, `bobix-linux-arm64.deb`), given by [the release workflow](../.github/workflows/release.yml), so `releases/latest/download/<name>` always serves the newest version. Keep the names there and the links in the READMEs and `docs/install.md` in step. Every push to `develop` builds them too: they are that run's artifacts on GitHub Actions, to try a build before it is released. Pull requests only run the smoke workflow; to try a PR's installers, start the release workflow by hand on its branch (Actions → release → Run workflow).

## Update feed

Bobix updates itself from signed update files ([update.rs](../src-tauri/src/update.rs), Tauri's updater plugin). The release workflow builds them next to the installers and a tag build publishes two update lists (a small JSON file naming the newest version, and for each system its file and signature):

| List | Where | Who reads it |
|---|---|---|
| `latest.json` | attached to each stable release: `releases/latest/download/latest.json` | everyone |
| `test.json` | attached to the pre-release `test-channel` (not a version: do not delete it, and never make it "latest"), replaced by every tag, stable or `-rc` (not a `-phones` tag, which is in no list): the newest build of any kind | only Settings → **Get test builds** on |

Both URLs are `plugins.updater.endpoints` in `tauri.conf.json` (stable first, test second). The update files are named like the installers (`Bobix-mac-arm64.app.tar.gz`, `Bobix-windows-x64.exe`, `bobix-linux-amd64.deb` and their `.sig`); [`update-manifest.mjs`](../.github/scripts/update-manifest.mjs) writes the lists and a tag build stops, before it publishes anything, when a file or a signature is missing. The app installs only a version greater than the running one, so a test build is never a step back from a release, and a release is a step up from its own test builds.

**Signing key (the owner's, never in the repository, a log or a session).** The key pair exists (key id `6C8CB60511EB2B2F`): its public key is in `plugins.updater.pubkey` of `tauri.conf.json`, and the private key and its password are secrets of the GitHub Environment `release`. The next step is a test tag (`v0.2.0-rc.N`) to prove a real signed update: install the previous test build by hand, tag the next one, turn on Get test builds, and update through the app. To make a new pair (a rotation, below):

1. On your own computer: `npm run tauri signer generate -- -w ~/bobix-updater.key`. It makes the private key (that file, protected by the password you type) and a public key (`bobix-updater.key.pub`).
2. Store them as secrets of the GitHub Environment `release` (Settings → Environments; only tags matching `v*` may use it), not as repository secrets: `gh secret set TAURI_SIGNING_PRIVATE_KEY --env release < ~/bobix-updater.key` (the file is read from your computer, nothing is printed) and `gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD --env release` (it asks for the password). Keep one backup of the key file and the password somewhere only you can open (a password manager).
3. Put the public key's contents (it is not secret) in `plugins.updater.pubkey` of `tauri.conf.json`, in a pull request. A build whose `pubkey` is not a public key (a placeholder) announces new versions with the link only: it cannot install them.

The key reaches only runs for a `v*` tag: a develop push or a run by hand builds the installers as before, with no update files. (The secrets live in the Environment `release`, which only `v*` tags may use, and the build job joins it only on a tag run. A tag runs the workflow of the commit it points at and tags are not protected, so the environment's tag rule is what keeps a branch from reaching the key.) A tag build stops before it publishes when the secrets are missing, `plugins.updater.pubkey` is still the placeholder, the tag is not `package.json`'s version, or an update file was signed with a key other than that public key's. **Rotating the key:** an installed Bobix checks signatures with the public key it was built with. Release one version that carries the **new** public key, signed with the **old** private key; once people are on it, sign with the new key. **If the private key is lost** with no such release made, no installed copy can update in-app again: publish a build with the new key, and tell people in the release notes to install it by hand (links in the [install guide](install.md)). The same hand install is needed once for anyone on a version from before the updater.

**Try an update on your own computer** (nothing of yours is touched): make a throwaway key (`tauri signer generate -w <scratch>/k.key`), build two versions with `tauri build --debug --config <file>` where the file sets `version`, `bundle.createUpdaterArtifacts`, `plugins.updater` (`pubkey` of the throwaway key, `endpoints` of `http://127.0.0.1:<port>/latest.json` and `/test.json`, `dangerousInsecureTransportProtocol: true`), sign with `TAURI_SIGNING_PRIVATE_KEY`, write the lists with `update-manifest.mjs --partial --base http://127.0.0.1:<port>`, serve the folder and open the older build with a scratch `BOBIX_HOME`, `BOBIX_DATA_DIR` and `BOBIX_PORT`. Delete the key afterwards.

## Branches

- **`main`** is the latest stable release and the default branch. It does not take direct changes: it moves to a new version only when that version is released as stable.
- **`develop`** is where work lands. Open pull requests against `develop`; every push to it builds the installers as artifacts, and pre-releases (`v0.2.0-rc.N`) are tagged from it.
- **`v1`** carries maintenance of the v1 line (Electron, v0.1.x) from the commit `main` had before 0.2.0. A fix for v1 is a pull request to `v1`, shipped as a `v0.1.x` tag on `v1`. Fix the same bug on `develop` too if the code still exists there. **The v1 line ends with 0.2.0:** once 0.2.0 is released, `v1` gets no more fixes.

`develop`, `main` and `v1` are protected: changes come in by pull request only (also for administrators), with no force push and no deletion. On `develop` and `main` the three smoke checks (`tauri (macos-latest)`, `tauri (windows-latest)`, `tauri (ubuntu-22.04)`) must pass before a pull request can merge; the smoke workflow runs on every pull request, whatever files it changes, so a docs-only pull request can merge too. It also runs on pushes and on `v*` tags, and the release workflow on `v*` tags, so both work on any of the three branches. Tags are not protected. Repository settings (branch protection, Dependabot alerts, private vulnerability reporting, the review secret) are the owner's: a session does not change them.

## Release

1. Bump `version` in `package.json` (the app reads it from there) on a branch such as `chore/release-0.2.0` cut from the branch you release from (`develop`, or `v1` for a v0.1.x fix), and open a pull request to that branch. Those branches are protected, so the bump cannot be pushed straight to them: the smoke checks run on the pull request and the owner merges it.
2. When it has merged, tag the merge commit: `git fetch origin && git tag v0.2.0 origin/develop && git push origin v0.2.0` (`origin/v1` for a v0.1.x fix). Tags are not protected. The release workflow builds on macOS, Windows and Ubuntu and attaches the installers to a GitHub Release. A tag with a dash (`v0.2.0-rc.1`) makes a pre-release, which does not become "latest".
3. Add release notes to the release. For a `v0.1.x` fix released from `v1` (the tag runs `v1`'s workflow): it must not become GitHub's "latest", or `releases/latest/download/latest.json` (the stable update list of the 0.2 line) stops existing and 0.2 users stop seeing new stable versions. Give `v1`'s release workflow `make_latest: false` for `v0.1.*` tags, as this branch's has, or run `gh release edit v0.1.x --latest=false` right after. The first release with the updater says so: copies before it (0.1.x and earlier test builds) update by hand once. Say too that **Get test builds** is off by default, so a tester on a test build sees the next one only after turning it on in Settings → App.
4. For a release with changes people should know about, rewrite the tour's steps (`STEPS` in `src/ui/tour.js`, each pointing at a real element, with its `tour.<key>.title` / `.body` strings in EN and VI), mark the one about this release `news: true`, and set `NEWS` in `src/ui/i18n.js` before tagging: the panel shows everyone updating to that version that one step once, as a single bubble (Done marks every step seen), never a new install; Setup → "Show the tour again" shows the whole tour. What a group or a setting does goes on its "?" instead (`HELP` in `src/ui/tour.js`, strings `help.grp.<key>` / `help.row.<key>`).

### Phone access is a compile switch

Phone access is still in development, so no build that ships has it, except the `-phones` pre-release described below. Settings → Phones, the ten `phones_*` Tauri commands and the relay link exist only in a build with the Cargo feature `phones` (`src-tauri/Cargo.toml`), which is **off by default**: a plain `cargo build`, a `develop` build, a `-rc` tag and a stable tag are all without it. It is on only when asked for: locally (`npm run tauri dev -- --features phones`, or `cargo run --features phones` in `src-tauri`), in the pull request smoke run (which builds and tests both configurations) and in a tag ending in `-phones`. A build with the feature accepts a plain `ws://` relay address on a private network (RFC 1918 or IPv6 unique-local) besides `wss://` and `ws://localhost`; a build without it never starts phone access. The plain `ws://` relay pairs only with the phone app's `dev` flavor (the TestFlight build); a `prod` phone build refuses `ws://`. On such a relay the relay's own frames are not sealed: see [privacy.md](privacy.md). Without the feature the section is not listed, the commands are not registered, not granted to the pages and not declared in `build.rs`, and `phones::init` returns first, so no thread, key, file or relay connection is made (the module's code is still in the binary; nothing starts it). The app's `state` carries `phones: true|false` for the panel. The smoke run's `phoneSwitch` step checks that the section and `phones_log` follow the build, and the release workflow requires `phoneSwitch.compiled` to be false, and true for a `-phones` tag. Try the build with it by hand:

```bash
cd src-tauri && cargo build --features phones   # the smoke command above then reports phoneSwitch.compiled true
```

The `command_list_tests` test keeps the handler, `COMMANDS` plus `PHONE_COMMANDS`, and `build.rs` in step in both configurations (run `cargo test` and `cargo test --features phones`). Taking the switch out for the public release means deleting the feature and the `cfg` attributes, and re-gating plain LAN `ws://` too (`relay_norm`'s `allow_lan` is tied to `ENABLED`, so removing the feature without that would let a stable build accept a plain-text relay); it is not part of the phone-access work.

#### Cutting a phones pre-release

Push a tag ending in `-phones`, on the commit to try (for example `git tag v0.2.0-rc.9-phones <commit> && git push origin v0.2.0-rc.9-phones`; the tag is not protected). `release.yml` then builds the installers on all three systems with `--features phones`, runs the same smoke on the installed apps and requires `phoneSwitch.compiled` to be true, and attaches the installers to a GitHub **pre-release** with that tag (never "latest"). It makes no update files (the signing key is not given to the build) and does **not** touch `latest.json`, the `test-channel` release or `test.json`, so no installed Bobix is offered this build and it needs no matching version in `package.json`. Anyone who wants it downloads the installer from that release by hand; a later normal build (without phones) updates over it as usual. Every other tag builds without the feature, as before. A `-phones` run does not join the `release` environment, so the signing key never reaches it. The in-app updater still runs in a `-phones` build: the next normal build with a strictly greater version installs over it and drops phone access, without the disconnect step (turn phone access off and disconnect each phone first); and a tester on `vX-phones` is not offered the normal build of the same `vX` (the versions are equal). The tag name does not choose the version: the app's version is still `package.json`'s.

## The link crate

`crates/bobix-link` holds the protocol and the crypto for phone access in one place: keys, the sealed packet, counters, messages, signed commands, the pairing code and the frames spoken to the relay. Every primitive comes from an audited RustCrypto crate; the crate decides only how they combine. It is a path dependency, not part of a Cargo workspace (`src-tauri` keeps its own `target`), and it does no file or network I/O, so the same code can sit behind the phone app's bindings. Nothing in `src-tauri` calls it yet.

```bash
cd crates/bobix-link && cargo test
```

- `tests/vectors.json` is a committed file with fixed keys, nonces and expected bytes. The tests compare against it and never rewrite it. After a deliberate wire change, run `cargo test --test vectors -- --ignored print_vectors`, review the diff and commit it. Signature vectors are verify-only (a phone's secure hardware does not sign the same bytes twice).
- `fuzz/` holds two cargo-fuzz targets (`open_envelope`, `parse_relay_frame`); they need a nightly toolchain: `cargo install cargo-fuzz && cd crates/bobix-link && cargo +nightly fuzz run open_envelope`. The `link` workflow runs each for 45 seconds on every pull request that touches the crate.
- Wire details a port must follow: `Home.rights` (set per phone in every `home`, and in one sent at once when the owner changes the phone's rights on the computer) is what that phone may do now, and the phone replaces its stored rights with it; absent (an older computer) means keep them; `SessionInfo.canStop` (set per phone: false unless that phone holds both the Stop and the Answer right) says Stop is possible (only for a session waiting on a held request; absent means false); a plan note and each answer to a question are at most 2000 bytes; a refused `start` carries the reason `folder` (the repository's folder is missing) or `disk` (not enough free space); `error { grant }` carries `peer`, the id of the phone whose push grant ended.
- The fake tools are examples and use made-up data only; they speak plain `ws://`, so use them with the in-process stub or with a relay started with `--dev` on localhost:
  ```bash
  cd crates/bobix-link
  cargo run --example relay-stub                      # prints ws://127.0.0.1:PORT
  cargo run --example fake-desktop -- --relay ws://127.0.0.1:PORT --scenario normal   # prints a QR string
  cargo run --example fake-phone -- --relay ws://127.0.0.1:PORT --qr 'bobix://pair?...'
  ```
  `fake-desktop --scenario list` names the 20 scenarios; `tests/fakes.rs` runs each of them in-process. `fake-phone` reads commands from standard input (the list is at the top of its source file) and signs with a software key.

[The link workflow](../.github/workflows/link.yml) runs on every pull request, but its jobs skip themselves when nothing under `crates/bobix-link/` changed (a skipped job counts as passing for a required check). Jobs: `link` on macOS, Windows and Ubuntu (clippy, tests, the fake tools built and kept as an artifact), `fuzz`, `audit` (known vulnerabilities in the dependencies, with cargo-deny), and `link-ok`, which fails when any of them failed. They have their own cache keys, so they never evict the app's cache. The owner makes `link-ok` a required check of `develop`, `main` and the phone-access integration branch `feat/phone-access` after the workflow has run once; it is the only name to require, because a skipped matrix job does not report one check per system.

## The phone app on Android

`mobile/android/` is the Android half of the phone app (app id `dev.bobix.phone`, Android 10 or later). The Dart code is shared with iOS; this is what is Android's own.

- **Build and run** (JDK 17 or later, the Android SDK, and the Rust Android targets: `rustup target add aarch64-linux-android x86_64-linux-android`): `cd mobile && flutter build apk --debug --dart-define=BOBIX_FLAVOR=dev` builds the debug app (cargokit builds the Rust core into it); `flutter run -d <emulator or phone> --dart-define=BOBIX_FLAVOR=dev` runs it. Flavors are the same Dart define as on iOS (`dev` allows plain `ws://` to localhost, `prod` the default does not). `flutter build apk --release --dart-define=BOBIX_FLAVOR=prod` builds what ships; without `mobile/android/key.properties` (git ignores it; keys `keyAlias`, `keyPassword`, `storeFile`, `storePassword`) it is signed with the debug key, which is never what ships. R8 runs on release builds; `app/proguard-rules.pro` keeps what JNA and the UniFFI binding look up by name.
- **The three keys** (`app/src/main/kotlin/dev/bobix/phone/keys/KeyStore.kt`, channel `dev.bobix.phone/secure_keys`, the same methods as iOS plus `strongBiometrics` and `signingKeyLevel`): `auth` and `box` are files in the app's no-backup folder encrypted with a Keystore AES key; `sign` is an ECDSA P-256 key in the Keystore (StrongBox where the phone has it) that needs a Class 3 biometric on every use, is invalidated when the enrolled biometrics change and has no passcode fallback. The first launch after an install erases every key. Nothing the app keeps is backed up (`allowBackup="false"` and both backup rule files exclude every domain). The emulator's Keystore is software-backed and `adb emu finger touch 1` stands in for a finger; to run the key tests without a person, use `--dart-define=BOBIX_SOFTWARE_KEY=true` (a Keystore key with no biometric requirement; the native side refuses it unless the app is debuggable): `flutter test integration_test/secure_keys_test.dart -d <emulator> --dart-define=BOBIX_SOFTWARE_KEY=true`.
- **Push** (`.../push/`): `PushService` (a `FirebaseMessagingService`, data messages only) opens the sealed notice with the `box` key through `open_notice` in `mobile/rust/src/push_opener.rs` (UniFFI; the same library `libbobix_phone_core.so` that flutter_rust_bridge loads), checks the `event` window in `PeerStore` (a file per computer under a file lock), and posts in the "Needs you" channel, private on the lock screen with a public version that says only "A session needs you". `waiting` replaces the notification of its `ref`, `closed` removes it, `done` has its own channel, and "Hide details" (read from `SharedPreferences` the app writes through the `dev.bobix.phone/push` channel) makes every notification generic. The channel `dev.bobix.phone/push` answers the contract the iOS push work defines (`lib/push/push_platform.dart`, `ios/Runner/PushChannel.swift`): same method names, argument names and answer maps (`permissionStatus`, `requestPermission`, `register`, `token`, `environment`, `grant`, `initialTap`, `setComputer`, `removeComputer`, `openPacket`, `hideDetails`, `setHideDetails`, `openSettings`; events `token`, `tokenError`, `tap` as `{computer, ref, kind}`); `PushChannel.kt` lists the Android specifics. A tap reaches Dart only when it carries a secret that only this app's own notifications have, but Dart must still treat it as input. The detail screens call `dev.bobix.phone/window` `setSecure(true)` to hide themselves from the recents screen.
- **Regenerating the Kotlin binding** after changing `push_opener.rs`: `cd mobile/rust && cargo build --features uniffi-cli && cargo run --features uniffi-cli --bin uniffi-bindgen -- generate --library target/debug/libbobix_phone_core.dylib --language kotlin --out-dir ../android/app/src/main/kotlin --no-format` (`.so` on Linux). CI fails when the committed `uniffi/bobix_phone_core/bobix_phone_core.kt` differs. The sealed notices the Kotlin tests use (`app/src/test/resources/notice-fixtures.json`) are made by a Rust test: `UPDATE_NOTICE_FIXTURES=1 cargo test` in `mobile/rust` rewrites them.
- **Tests**: `cd mobile/rust && cargo build && cd ../android && ./gradlew :app:testDebugUnitTest` runs the Kotlin unit tests on this computer (the opener through the real Rust library, the decision per notice kind and the Hide details switch, two pushes at once, the biometric error mapping, the manifest's backup and service settings). A debug build also contains `DebugPush`, a receiver (protected by the `DUMP` permission, so only `adb` can reach it) that lets `adb` seed a computer and deliver a sealed notice without Firebase (see `app/src/debug/kotlin/dev/bobix/phone/debug/DebugPush.kt`); release builds do not.
- **Outside the app** (`app/src/main/kotlin/dev/bobix/phone/surfaces/`): three Glance home screen widgets (2×2, 4×2, 4×4), an ongoing "waiting requests" notification (a Live Update on Android 16, an ordinary ongoing one with an indeterminate bar below it, private on the lock screen), and two Quick Settings tiles ("Bobix" with the count, "Start"). They read one small list, `surfaces/list.json` in the app's no-backup files, plus the pet images in `surfaces/pets/` (`<design>-<colour>-<state>.png`, drawn by `lib/surfaces/pet_png.dart` from the same SVG as the app). It is the same shared list the iOS widgets read (`lib/surfaces/shared_list.dart` writes it; Android parses it in `SurfaceList.kt`). The app writes it at every `home` through the same code as on iOS (`lib/surfaces/surfaces_sync.dart`, over the channel `dev.bobix.phone/surfaces`, which Kotlin answers in `SurfacesChannel.kt`) and clears it when nothing is paired (Disconnect, Erase and pair again, a `revoked` from the computer); the push service changes it by each notice (`waiting` adds, `closed` removes, and only that item gets a new time) and redraws everything. Writes go through one lock (a file lock plus a monitor) and a uniquely named temp file. The list holds names, counts, pets and times, never a command, a tool input or a plan, and no protocol logic is in Kotlin. **Staleness** (`SurfaceModel`, decision 24): each waiting item carries the time it was last confirmed (the list's write time, or the notice's for an item only a push told us about); an item older than 15 minutes, or older than the wait the computer still held for it (`holdSecs`, so a wait under 15 minutes dims at the wait), is not counted, and the list "nothing waits" claim is stale after 15 minutes; when nothing fresh is left the surface is stale, meaning the dimmed "Updated hh:mm" instead of "needs you". The app writes the list again every 5 minutes while the computer is reachable (`SurfacesHost`, so a reachable computer does not go stale), counting the seconds a request still holds down from when the data was made; the rewriting also stops while the app is not on the screen (a lifecycle listener in `SurfacesHost`), so the data ages, and it keeps saying what the computer last said: leaving the app does not mark the computer offline. An alarm redraws everything at the moment something turns stale: it is inexact on purpose (`AlarmManager.set`, no exact-alarm permission; a few minutes late is normal, and a battery manager may delay it more), it is set again at boot (`StaleReceiver`, `RECEIVE_BOOT_COMPLETED`), by every widget update and by the tile listening, and the Live Update has a timeout at the same moment. The widgets read the list inside their composition, keyed on a counter that `Surfaces.refresh` bumps, so a widget that is already on the screen redraws (one Glance class per size). Glance brings WorkManager into the manifest (`RECEIVE_BOOT_COMPLETED`, a foreground service type for its workers); the app starts no work of its own with it. A push changes the list only for a notice whose sealed box opened, and only by its kind and `ref`: a title or body the relay could supply is never drawn. "Hide details" leaves counts only, keeps no session or project name in the stored list (the store drops them on every write while the switch is on, and once when it is switched on; switching it off asks the app to write the list again), and redraws the widgets, the Live Update and the tiles in one pass the moment the switch changes. Every tap opens the app through `Surfaces.openIntent`, signed with the app's secret like a notification tap: the first waiting request, Home when nothing waits or the data is stale, or the Start tab. A tap reaches Dart as a tap of the push channel (`PushChannel.onIntent`, kind `waiting`, `home` or `start`), the same path as a notification tap, and a request tap that starts the app waits for the first `home`. The "stale" lines say `Computer offline` or `Computer asleep` when the list said so. The strings are the `phone.wg.*` keys shared with iOS. The app lock sits above the shell, so the tapped screen is drawn only after the unlock; nothing answers, and the answer still needs the fingerprint. Remove the receivers and services of that block in `AndroidManifest.xml` and the app is unchanged. In a debug build `DebugPush` can write a list for you (`SURFACES`, see its header) and `WidgetPreview` hosts the real widgets in one activity for screenshots (the system asks once per widget to allow it: tick "Always allow" and Create); add a tile with `adb shell cmd statusbar add-tile dev.bobix.phone/dev.bobix.phone.surfaces.BobixTile`. Android 16 asks `POST_PROMOTED_NOTIFICATIONS` (declared) for the Live Update.
- **Firebase (owner step, milestone 2)**: the app builds and runs without a Firebase project; the push service then never receives anything and the `push` channel's `token` answers null. To turn push on, create a Firebase project with an Android app `dev.bobix.phone`, download its `google-services.json` and put it in `mobile/android/app/` (git ignores it; do not commit it). The Gradle build applies the Google services plugin when the file is there. Firebase's init provider still sets up `FirebaseApp` at every launch once the file is there; what stays off until the app asks (after pairing) is fetching the token and its installation id, and analytics.
- **Gradle and Flutter versions**: CI pins Flutter 3.47.9; `mobile/android` uses Android Gradle Plugin 9.1.1, Kotlin 2.4.20 and Gradle 9.5.0, which that Flutter accepts. A newer Flutter on a developer machine may warn that the AGP is old; it still builds.

## The relay

`relay/` is an axum server (a path dependency on `bobix-link`, its own `Cargo.lock`, not part of a workspace). It authenticates a device with a challenge signed by its `auth` key, keeps one in-memory mailbox per recipient (ttl at most 600 s, 64 packets, 2 MiB) until the recipient acknowledges, delivers only between devices that allowed each other, forwards up to four `pairSend`s per open pairing token, shows presence (`online`, `offline` after 30 s without a pong, `asleep`), keeps revocations in a small file per desktop for 90 days (a revocation cuts only the path between that desktop and that device; the device is told with `error { revoked }` and keeps its other desktops), and with `INVITE_FILE` set serves only invited computers. Pushes go through a `PushSender` (APNs, FCM, another relay's gateway, or a recording fake); `POST /v1/push` is the gateway for relays without credentials. It never parses a `body` and has no code or dependency that could open one. Only a relay with its own APNs or FCM credentials (or `--dev`) serves the gateway route.

```bash
cd relay && cargo test
cargo run -- --dev          # plain ws on 127.0.0.1:8787, recording push fake, GET /healthz, GET /dev/pushes
```

- Configuration is by environment variables only; without `--dev`, `RELAY_PUBLIC_URL` (the relay's own address as devices know it, such as `wss://relay.example`; a device signs it when it logs in, so a signature made for another relay is refused with `relayUrl`, and a wrong value shows in the log as "signed for … but this relay's RELAY_PUBLIC_URL is …"), `RELAY_ID` (the id push grants name) and `REVOKED_DIR` are required and the relay says which one is missing. With `--dev` the public URL is `ws://` plus the bind address unless `RELAY_PUBLIC_URL` is set. Others: `RELAY_ADDR` (default `0.0.0.0:8787`; `127.0.0.1:8787` with `--dev`), `INVITE_FILE` (one device id per line, `#` comments), `GATEWAY_KEYS_FILE` (one gateway key per line, optionally followed by the relay id it belongs to), `LOG_DIR` (one file per day, 14 days kept), `APNS_KEY_FILE` with `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_TOPIC`, `FCM_SERVICE_ACCOUNT_FILE`, and `PUSH_GATEWAY_URL` with `PUSH_GATEWAY_KEY_FILE`. Credentials are read from the files named, never from the repository.
- `--dev` refuses to listen on anything but loopback (it keeps no revoked list on disk and sends no real push); `RELAY_DEV_FORCE_BIND=1` overrides this on purpose and the relay says so at start; it then also needs `RELAY_PUBLIC_URL` (the address devices use, such as `ws://192.168.1.20:8787`), because there is no address to derive from `0.0.0.0`.
- Limits: a socket has a queue of 256 outbound frames and is closed when it is full (a reader that does not read); a device may send 100 frames a second; a client address (an IPv6 one counts by its /64) may hold 8 sockets that have not authenticated and 32 sockets in all, and open 120 connections a minute; 1000 mailboxes and 256 MiB at most are held in all; one IPv6 /48 may hold 32 unauthenticated sockets, and over all addresses at most 256 sockets may be unauthenticated and 4096 open; with invitations on, a guest that names no invited computer in `peers` within 30 seconds is closed; the allow-list and push tokens of a device that left are dropped after an hour; pushes through the relay's own credentials are limited per token and per sending device. The client address is the connection's, or, behind a proxy you trust, the last value of the header `CLIENT_IP_HEADER` names (for example `X-Forwarded-For`); set it only when the proxy overwrites that header, otherwise a client could pick its own address. `INVITE_FILE` is looked at again every 5 seconds, also for desktops that are connected. `PUSH_GATEWAY_URL` must be `https://` (plain `http://` only with `--dev`).
- A desktop can revoke only a device that confirmed a pairing with it, meaning it sent the desktop a packet the desktop had allowed; that record is kept next to the revoked list (`<desktop id>.paired` in `REVOKED_DIR`, 90 days), so a revoke works after a relay restart. A desktop that merely received a `hello` cannot affect the phone. A fresh pairing the desktop opens lifts an old cut.
- `--dev` also serves the socket on `/`, because the fake tools of the link crate connect to exactly the address they are given: `fake-desktop --relay ws://127.0.0.1:8787`. A real client connects to `/v1/ws`.
- Logs hold device ids and counts, never a body or a token (`tests/push.rs` checks this).
- Deploy: [`relay/README.md`](../relay/README.md) covers what the relay can see, self-hosting, every setting and the Railway steps; `relay/Dockerfile` is built from the repository root (`docker build -f relay/Dockerfile .`). Not done yet: the deploy itself.

`GET /healthz` answers `200 ok`, or `503` with `invitation file missing or unreadable` / `gateway keys file missing or unreadable` when `INVITE_FILE` or `GATEWAY_KEYS_FILE` is set and cannot be read (never the path). [`relay-health.yml`](../.github/workflows/relay-health.yml) calls it every 15 minutes at the repository variable `RELAY_URL` and fails the run (which GitHub mails) when it does not answer `ok`; without the variable it does nothing.

[The relay workflow](../.github/workflows/relay.yml) mirrors the link workflow: it skips its jobs when nothing under `relay/` or `crates/bobix-link/` changed; jobs `relay` (clippy and tests on macOS and Ubuntu), `audit` (cargo-deny) and `relay-ok`, the one check to require.

## Try the phone app on a real iPhone

To try the phone app on your own iPhone with a relay and a desktop on your own Mac, over the home Wi-Fi (no server, no
account at Apple beyond a free developer team to sign the app). Everything stays on your network; the relay is `relay --dev`
(plain `ws://`, nothing kept on disk, no real push). Both devices must be on the same Wi-Fi, and the Wi-Fi must let devices
talk to each other (a guest network or "client isolation" blocks it).

1. **The Mac's address.** `ipconfig getifaddr en0` (the Wi-Fi; `en1` on some Macs). Say it is `192.168.1.20`; use yours below. It
   must be a private address (`10.x.x.x`, `172.16.x.x` to `172.31.x.x` or `192.168.x.x`; an IPv6 unique-local `fd..` one works too):
   a plain `ws://` address is accepted only for those and for `localhost`, never for a name (not even `*.local`), a public address or
   a link-local one (`169.254.x.x`, `fe80::`; a cable-only Mac-to-iPhone link is not supported). Give the Mac a fixed address in your
   router if you want the setup to survive a restart.
2. **The relay, listening on the network.** `--dev` listens on loopback only; this is the one place to widen it. It needs the address
   phones use, because every device signs that address when it logs in, and `0.0.0.0` is not one:

   ```bash
   cd relay
   RELAY_DEV_FORCE_BIND=1 RELAY_ADDR=0.0.0.0:8787 RELAY_PUBLIC_URL=ws://192.168.1.20:8787 cargo run -- --dev
   ```

   Without `RELAY_PUBLIC_URL` it stops and says so. `curl http://192.168.1.20:8787/healthz` from another device should answer `ok`.
   macOS may ask to allow incoming connections for `bobix-relay`: allow it. Stop the relay when you are done: anything on the
   Wi-Fi can reach it meanwhile (packets are sealed end to end, but anyone could open a pairing on it).
3. **The desktop.** Phone access is in a build only with the `phones` Cargo feature, off by default (see [Phone access is a compile switch](#phone-access-is-a-compile-switch)). Run it with `--features phones` and its own data so it does not touch your installed
   Bobix or your real keys (with `BOBIX_DATA_DIR` set, the keys go to a file in it and never to the Keychain):

   ```bash
   BOBIX_PORT=4767 BOBIX_DATA_DIR=/tmp/bobix-data BOBIX_HOME=/tmp/bobix-home npm run tauri dev -- --features phones
   ```

   Open the panel, Settings → Phones. Type `ws://192.168.1.20:8787` in **Relay address** and save, then turn on **Let phones connect**.
   The status says "connected". (If it says "the relay does not recognise its own address", the address here and `RELAY_PUBLIC_URL`
   differ.) A plain `ws://` address is accepted here only for those private addresses.
4. **The phone app on the iPhone.** Needs Xcode, Flutter (the version `mobile.yml` pins) and the iPhone connected (turn on Developer Mode
   in the iPhone's Settings → Privacy & Security). Once:

   ```bash
   cd mobile
   cp ios/Flutter/Local.xcconfig.example ios/Flutter/Local.xcconfig   # git ignores it; put your Apple team id in DEVELOPMENT_TEAM
   open ios/Runner.xcworkspace   # Runner → Signing & Capabilities: choose your team; if the bundle id dev.bobix.phone is taken, change it here only
   ```

   Then build and run it in the `dev` flavor, which is the one that allows a plain `ws://` address (the default `prod` flavor never does):

   ```bash
   flutter run -d <your iPhone> --dart-define=BOBIX_FLAVOR=dev
   ```

   The first run asks to trust the developer on the iPhone (Settings → General → VPN & Device Management). The app asks for the camera
   (to read the code), Face ID and, when it first connects, **Local Network**: allow all three. Without Local Network the connection
   fails silently; if it was refused, turn it on in Settings → Bobix.
5. **Pair.** In Settings → Phones on the desktop press **Pair a phone**; in the app choose to connect a computer and scan the code
   (it works for 2 minutes). Back on the desktop, choose what the phone may do and press **Connect**. The phone then shows the
   computer and what it may do. Face ID is asked each time the phone signs a command (an answer, an approval).
6. **What works without push.** Whatever the app on your branch has of the phone screens (pairing, the home list of sessions and
   pets, requests, plans and questions with Face ID; [roadmap.md](roadmap.md) says what is built), while the app is open and the
   Mac and iPhone are on the same Wi-Fi. What does not: notifications while the app is closed (the relay has no APNs credentials
   and `--dev` sends no real push), and anything after leaving the Wi-Fi or stopping the relay (nothing is kept: pair again after a
   relay restart only if the desktop says so).

On a simulator the same steps work except for the camera: the `dev` flavor shows a text field on the pairing screen where you paste
the code the desktop shows (use the simulator with `--dart-define=BOBIX_SOFTWARE_KEY=true`, because it has no Face ID).
